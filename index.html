    Chapter 6 — Synchronization Tools

    Big picture. When several processes or threads share data and run at the same time, their instructions can interleave in unlucky ways and corrupt the data. This chapter builds up, from the bottom, the tools that stop that from happening: first pure software (Peterson), then hardware instructions (test-and-set, compare-and-swap), then the OS tools that programmers actually use (mutex locks, semaphores, monitors with condition variables). It ends with what can still go wrong (liveness failures: deadlock, starvation, priority inversion). 6.2–6.3

    Objectives listed on slide 6.3: describe the critical-section problem and illustrate a race condition; illustrate hardware solutions (memory barriers, compare-and-swap, atomic variables); demonstrate mutex locks, semaphores, monitors, and condition variables; evaluate tools in low-, moderate- and high-contention scenarios.

    6.1 Background and race conditions 6.4–6.5

    Definitions

    Concurrent execution: processes run at the same time (or interleaved); a process may be interrupted at any time, leaving its work partially done.

    Cooperating processes: processes that share data. Concurrent access to shared data may result in data inconsistency, so we need mechanisms that ensure their orderly execution.

    Race condition: a situation where several processes access and change the same shared data concurrently, and the result depends on the order in which the accesses happen.

    The slide reminds you of the Chapter 4 bounded-buffer example: a producer and a consumer both update a shared counter (counter++ / counter--). Each update is really load → change → store, so if the two interleave, one update can be lost — a race condition.

    Slide example: two fork() calls race on next_available_pid

    6.2 The critical-section problem 6.6–6.8

    Consider a system of n processes {p0, p1, … pn−1}. Each process has a critical section (CS): a segment of code in which it may be changing common variables, updating a table, writing a file, etc. The rule: when one process is in its critical section, no other may be in its critical section. The critical-section problem is to design a protocol that enforces this.

    Three requirements of any correct solution
    1. Mutual exclusion — if Pi is executing in its CS, no other process can be executing in its CS.
    2. Progress — if no process is in its CS and some processes want to enter, the selection of who enters next cannot be postponed indefinitely (and only processes that want to enter take part in the decision).
    3. Bounded waiting — after a process requests entry, there is a bound on how many times other processes may enter their CS before this request is granted.

    Assumptions: each process executes at a nonzero speed; no assumption about the relative speed of the n processes.

    How to check a proposed solution (exam recipe)
    • Mutual exclusion? Try to construct an interleaving where both are inside. If you can, it fails.
    • Progress? Look for a case where the CS is empty, someone wants in, but they are stuck because of a process that is not interested (e.g., in its remainder section).
    • Bounded waiting? Look for a case where one process can be overtaken again and again forever (e.g., a lock that is grabbed by whoever happens to be fastest).

    6.3 Interrupt-based solution 6.9

    Idea: entry section = disable interrupts; exit section = enable interrupts. With no interrupts, the running process cannot be preempted on that CPU, so nobody else runs during the CS.

    Slide question: “Will this solve the problem?” — Answer
    • What if the CS runs for an hour? Then for an hour no interrupts are handled (timer, I/O) — the system is frozen for everyone else. Unacceptable for user code.
    • Can some processes starve? Yes — nothing decides fairly who enters next, so a process can be passed over indefinitely (no bounded waiting).
    • What if there are two CPUs? Disabling interrupts only affects the CPU that executes the instruction. A process on the other CPU can still enter its CS at the same time, so mutual exclusion fails on multiprocessors (and disabling on all CPUs is too slow — see 6.23).

    Conclusion: only workable for very short kernel code on a uniprocessor.

    6.4 Software Solution 1 (strict alternation with turn) 6.10–6.12

    Two-process solution (Pi and Pj, where j = 1 − i). Assumption: load and store machine instructions are atomic (cannot be interrupted). Shared variable: int turn; — whose turn it is to enter. Initially turn = i.

    while (true){
    while (turn == j);      // busy-wait while it is the other's turn
        /* critical section */
    turn = j;                // give the turn to the other process
        /* remainder section */
}
    Slide 6.12: correctness — answers

    Mutual exclusion: preserved. Pi enters only if turn == i, and turn cannot be both 0 and 1 at the same time.

    Progress: NOT satisfied. The processes must strictly alternate. Example: turn = 0, P0 is in a long remainder section and does not want the CS. P1 wants to enter, the CS is empty, but P1 spins on while(turn==0) until P0 comes back, enters and leaves. A process that is not interested is blocking the decision.

    Bounded waiting: satisfied. After Pi asks, Pj can enter at most once before Pi (because Pj's exit sets turn = i). Bound = 1.

    6.5 Peterson's Solution 6.13–6.15

    Fixes the progress problem by adding a “do you want in?” flag. Two-process solution, again assuming atomic load/store. Shared variables:

    • int turn; — whose turn it is to enter the CS (used as a tie-breaker).
    • boolean flag[2]; — flag[i] = true means process Pi is ready (wants to enter). Initially both false.
    1 while (true){
2     flag[i] = true;               // I want to enter
3     turn = j;                     // ...but politely let you go first
4     while (flag[j] && turn == j)  // wait only if you want in AND it's your turn
5         ;
6         /* critical section */
7     flag[i] = false;              // I no longer want in
8         /* remainder section */
9 }

    Order of operations matters: set your flag first, then give away the turn, then test. Pi enters the CS only if either flag[j] == false or turn == i.

    Trace: both arrive at the same time

    StepActionflag[0]flag[1]turnResult
    0initialFF–
    1P0: flag[0]=trueTF–
    2P1: flag[1]=trueTT–
    3P0: turn=1TT1

    5P0 tests flag[1]&&turn==1TT0T && F = false → P0 enters
    6P1 tests flag[0]&&turn==0TT0T && T = true → P1 waits
    7P0 exits: flag[0]=falseFT0P1's test becomes false → P1 enters

    Rule to remember: when both want in, the process that wrote turn last waits (it gave the turn away last). Since turn holds only one value, exactly one gets in.

    Why all three requirements hold 6.15
    1. Mutual exclusion: to both be inside, we'd need (flag[1]==false or turn==0) and (flag[0]==false or turn==1). Both flags are true while both are trying, so we'd need turn==0 and turn==1 simultaneously — impossible.
    2. Progress: if Pj is not interested, flag[j]==false and Pi enters immediately — an uninterested process never blocks.
    3. Bounded waiting: when Pj leaves and tries again, it sets turn = i, so Pi gets in — Pi waits for at most one entry by Pj.

    6.6 Modern architectures, instruction reordering & memory barriers 6.16–6.22

    Peterson's solution is useful for demonstrating an algorithm, but it is not guaranteed to work on modern architectures: to improve performance, processors and/or compilers may reorder operations that have no dependencies. For single-threaded programs this is fine (the result is always the same); for multithreaded programs reordering may give inconsistent or unexpected results. Understanding why helps you understand race conditions.

    Slide example 6.17–6.18

    Shared: boolean flag = false; int x = 0;

    // Thread 1
while (!flag)
    ;
print x;
    // Thread 2
x = 100;
flag = true;

    Expected output: 100. But flag and x are independent, so Thread 2's two stores may be reordered to flag = true; x = 100;. Then Thread 1 may see flag true, leave its loop, and print 0 before x = 100 happens. (Thread 1's loads could likewise be reordered, loading x before flag.)

    Memory model & memory barrier 6.20–6.21

    Memory model = the memory guarantees a computer architecture makes to application programs. Either:

    • Strongly ordered — a memory modification by one processor is immediately visible to all other processors.
    • Weakly ordered — a modification by one processor may not be immediately visible to others.

    Memory barrier (memory fence) = an instruction that forces any change in memory to be propagated (made visible) to all other processors. When it executes, the system ensures all loads and stores before it are completed before any subsequent load or store is performed. So even if instructions were reordered, stores are completed and visible before later loads/stores.

    Fixing the example with barriers 6.22

    // Thread 1
while (!flag)
    memory_barrier();
print x;
    // Thread 2
x = 100;
memory_barrier();
flag = true;

    Thread 1: guaranteed that flag is loaded before x. Thread 2: guaranteed that the assignment to x happens before the assignment to flag. Output is now always 100.

    6.7 Hardware support: test_and_set and compare_and_swap 6.23–6.29

    Many systems provide hardware support for critical-section code. On uniprocessors we could disable interrupts (running code executes without preemption), but this is generally too inefficient on multiprocessor systems — operating systems using it are not broadly scalable. The slide then lists the hardware support studied: 1. hardware instructions, 2. atomic variables (memory barriers, covered above, are the third form in the textbook).

    Hardware instructions let us either test-and-modify the content of a word, or swap the contents of two words atomically (uninterruptedly): the Test-and-Set and Compare-and-Swap instructions.

    test_and_set 6.25–6.26

    boolean test_and_set(boolean *target) {
    boolean rv = *target;   // remember old value
    *target = true;          // always set to true
    return rv;               // return OLD value
}                            // the whole function executes ATOMICALLY

    Properties: executed atomically; returns the original value of the passed parameter; sets the new value to true.

    // shared: boolean lock = false;
do {
    while (test_and_set(&lock))
        ;  /* do nothing */
        /* critical section */
    lock = false;
        /* remainder section */
} while (true);

    How it works: if lock was false, test_and_set returns false (you exit the loop and enter) and has already set lock to true, so everyone else gets true back and spins. Because the read-and-set is one atomic step, two processes can never both read false.

    Slide 6.26 & 6.28: “Does it solve the critical-section problem?” — Answer

    Mutual exclusion: yes. Progress: yes (if the lock is free, a contender gets it). Bounded waiting: NO — when the lock is released, whichever spinning process happens to execute test_and_set first wins; an unlucky process can lose every time. Same answer for the simple compare_and_swap lock. This is why slide 6.29 exists.

    compare_and_swap (CAS) 6.27–6.28

    int compare_and_swap(int *value, int expected, int new_value) {
    int temp = *value;
    if (*value == expected)
        *value = new_value;
    return temp;
}                            // executes ATOMICALLY

    Properties: executed atomically; returns the original value of *value; sets *value to new_value only if *value == expected — the swap takes place only under this condition.

    // shared: int lock = 0;   (0 = free, 1 = taken)
while (true){
    while (compare_and_swap(&lock, 0, 1) != 0)
        ;  /* do nothing */
        /* critical section */
    lock = 0;
        /* remainder section */
}

    “If lock is 0, make it 1 and tell me it was 0.” Returned 0 → you got the lock. Returned 1 → someone has it; keep trying.

    Bounded-waiting mutual exclusion with compare-and-swap 6.29

    Shared: boolean waiting[n] (all false), int lock = 0. Local: key, j. Process Pi:

     1 while (true) {
 2     waiting[i] = true;                 // I am waiting
 3     key = 1;
 4     while (waiting[i] && key == 1)       // leave when lock grabbed OR handed to me
 5         key = compare_and_swap(&lock,0,1);
 6     waiting[i] = false;
 7         /* critical section */
 8     j = (i + 1) % n;                    // scan the others in cyclic order
 9     while ((j != i) && !waiting[j])
10         j = (j + 1) % n;
11     if (j == i)
12         lock = 0;                       // nobody waiting: free the lock
13     else
14         waiting[j] = false;             // hand the CS directly to Pj (lock stays 1)
15         /* remainder section */
16 }

    Key lines: line 4 — a process leaves the spin loop in exactly two ways: it grabbed a free lock (key becomes 0) or another process set its waiting[i] to false (handed over). Lines 8–14 — on exit, scan i+1, i+2, … cyclically for the first waiting process; pass the CS straight to it without releasing the lock; release only if nobody waits.

    Why bounded waiting holds

    The leaving process always picks the next waiting process in cyclic order. So a waiting process is passed over by at most n − 1 other entries before its turn.

    6.8 Atomic variables 6.30–6.31

    Instructions like CAS are used as building blocks for other synchronization tools. One such tool is an atomic variable: it provides atomic (uninterruptible) updates on basic data types such as integers and booleans. If sequence is an atomic variable, increment(&sequence); ensures it is incremented without interruption. Implementation with CAS:

    void increment(atomic_int *v) {
    int temp;
    do {
        temp = *v;                                     // read current value
    } while (temp != (compare_and_swap(v, temp, temp+1)));  // retry if someone changed it
}

    Why the loop: CAS writes temp+1 only if *v still equals the temp we read. If another thread changed *v in between, CAS returns a value ≠ temp, nothing is written, and we retry with the fresh value. No update is ever lost.

    Exam trap

    Atomic variables make a single update atomic. They do not solve every race (e.g., they don't make a multi-variable update or a “check-then-act” sequence atomic). They're ideal for counters and sequence generators.

    6.9 Mutex locks 6.32–6.33

    The previous solutions are complicated and generally inaccessible to application programmers, so OS designers build software tools. The simplest is the mutex lock (mutex = mutual exclusion): a boolean variable indicating whether the lock is available.

    • Protect a CS by first acquire()-ing the lock, then release()-ing it.
    • Calls to acquire() and release() must be atomic — usually implemented via hardware atomic instructions such as compare-and-swap.
    • But this solution requires busy waiting (looping while waiting for the lock) → this lock is therefore called a spinlock.
    while (true) {
    acquire lock
        critical section
    release lock
        remainder section
}
    When is spinning OK?

    Busy waiting wastes CPU cycles, but it avoids a context switch. Spinlocks are good when locks are held for a very short time on a multiprocessor; bad when the CS is long or there is only one CPU (the holder can't run while you spin).

    6.10 Semaphores 6.34–6.41

    A semaphore is a synchronization tool that provides more sophisticated ways (than mutex locks) for processes to synchronize. A semaphore S is an integer variable accessed only through two indivisible (atomic) operations: wait() and signal() — originally called P() (wait) and V() (signal).

    // busy-waiting definition
wait(S) {
    while (S <= 0)
        ; // busy wait
    S--;
}
    signal(S) {
    S++;
}

    Meaning: S counts available “permits”. wait takes a permit (waiting while none is available); signal returns one.

    Counting vs binary 6.35
    • Counting semaphore — value ranges over an unrestricted domain. Use it to control access to a resource with several instances (initialize to the number of instances).
    • Binary semaphore — value only 0 or 1; same as a mutex lock.
    • A counting semaphore S can be implemented using binary semaphores. With semaphores we can solve various synchronization problems.

    Usage patterns 6.36

    1. Mutual exclusion — semaphore mutex initialized to 1:

    wait(mutex);
    CS
signal(mutex);

    2. Ordering — S1 in P1 must happen before S2 in P2: semaphore synch initialized to 0:

    // P1:          // P2:
S1;               wait(synch);
signal(synch);    S2;

    Why ordering works: synch starts at 0, so P2's wait cannot get past until P1 has done S1 and then signal. If P1 runs first, synch becomes 1 and P2 passes straight through — either way S1 precedes S2.

    Choosing the initial value — the most tested skill
    • 1 → mutual exclusion (one process at a time).
    • 0 → “wait for an event”: the first wait blocks until someone signals.
    • n → n identical resources / n free slots.

    Implementation 6.37

    We must guarantee that no two processes execute wait() and signal() on the same semaphore at the same time. So implementing a semaphore is itself a critical-section problem, where the wait/signal code is the CS. We could use busy waiting inside that implementation: the code is short, so there is little busy waiting if the CS is rarely occupied. But applications may spend lots of time in their own critical sections, so busy-waiting semaphores are not a good general solution.

    Implementation with no busy waiting 6.38–6.40

    Each semaphore has an associated waiting queue. Each entry has two data items: a value (integer) and a pointer to the next record in the list. Two OS operations:

    • block — place the process invoking the operation on the appropriate waiting queue (it stops using the CPU).
    • wakeup — remove one process from the waiting queue and place it in the ready queue.
    typedef struct {
    int value;
    struct process *list;
} semaphore;

wait(semaphore *S) {
    S->value--;                     // 1. decrement FIRST
    if (S->value < 0) {             // 2. then test
        add this process to S->list;
        block();
    }
}
signal(semaphore *S) {
    S->value++;                     // 1. increment FIRST
    if (S->value <= 0) {            // 2. someone was waiting
        remove a process P from S->list;
        wakeup(P);
    }
}
    Operation order — the details that change exam answers
    • In this version wait decrements first, then tests < 0; signal increments first, then tests <= 0.
    • So the value can become negative. If value = −k, then k processes are waiting in the list.
    • In the busy-waiting definition (6.34) wait tests first (while S<=0) then decrements, so the value never goes below 0.
    • signal wakes up one process (if any); it never blocks.

    Problems with semaphores 6.41

    Incorrect use of semaphore operations causes serious bugs:

    • signal(mutex) … wait(mutex) (reversed) → several processes can be in the CS at once (mutual exclusion violated).
    • wait(mutex) … wait(mutex) (signal replaced by wait) → the process blocks on its own second wait forever → deadlock.
    • Omitting wait(mutex) and/or signal(mutex) → either no mutual exclusion, or the lock is never released and others block forever.

    These, and others, are what happen when semaphores and other tools are used incorrectly — the motivation for monitors.

    6.11 Monitors and condition variables 6.42–6.47

    Monitor

    A high-level abstraction (an abstract data type) that provides a convenient and effective mechanism for process synchronization. Its internal variables are only accessible by code within its procedures, and only one process may be active within the monitor at a time — mutual exclusion is automatic; the programmer cannot forget a wait/signal.

    monitor monitor-name
{
    // shared variable declarations
    procedure P1 (…) { …. }
    procedure P2 (…) { …. }
    procedure Pn (…) {……}
    initialization code (…) { … }
}
    Condition variables 6.45

    condition x, y; Two operations:

    • x.wait() — the invoking process is suspended until x.signal().
    • x.signal() — resumes one of the processes (if any) that invoked x.wait(). If no process is waiting on x, it has no effect.
    Condition-variable signal vs semaphore signal (classic confusion)

    Semaphore signal() always changes the value (S++) — the signal is “remembered”: a later wait() passes straight through. Condition x.signal() with nobody waiting is lost — a later x.wait() still blocks. That is why the next example needs the extra done flag.

    Example: S1 before S2 with a monitor 6.47

    Monitor with procedures F1 (called by P1) and F2 (called by P2), one condition variable x, and a Boolean done (initially false).

    // F1:
S1;
done = true;
x.signal();
    // F2:
if (done == false)
    x.wait();
S2;

    If F1 runs first, its x.signal() is lost — but done is already true, so F2 doesn't wait. If F2 runs first, done is false, so P2 waits until F1 signals.

    Slide quirk

    Slide 6.47 says the condition variable “x initialized to 0”. Condition variables have no value (only a queue); the slide is borrowing semaphore language. The done flag carries the “state”.

    6.12 Implementing a monitor with semaphores 6.44, 6.48–6.50

    Simple version (no condition variables) 6.44: one semaphore mutex = 1; each procedure P becomes wait(mutex); … body of P; … signal(mutex);. Mutual exclusion within the monitor is ensured.

    Full version (with condition variables). When P signals x and wakes Q, both can't run inside the monitor. In this implementation the signaler waits (on semaphore next) while the woken process runs (signal-and-wait).

    // Monitor-wide variables
semaphore mutex;      // (initially = 1)  — entry to the monitor
semaphore next;       // (initially = 0)  — signalers suspend here
int next_count = 0;   // number of processes suspended on next (waiting inside the monitor)

// Each function P is replaced by:
wait(mutex);
    …  body of P  …
if (next_count > 0)
    signal(next);     // let a suspended signaler continue
else
    signal(mutex);    // otherwise open the monitor to newcomers

// For each condition variable x
semaphore x_sem;      // (initially = 0)
int x_count = 0;      // number of processes waiting on x

// x.wait()
x_count++;
if (next_count > 0)
    signal(next);     // pass the monitor to a suspended signaler
else
    signal(mutex);    // or release the monitor
wait(x_sem);          // sleep until signaled
x_count--;

// x.signal()
if (x_count > 0) {    // only if someone waits on x (else: no effect)
    next_count++;
    signal(x_sem);    // wake one waiter
    wait(next);       // and suspend myself
    next_count--;
}

    6.13 Resuming processes in a monitor; single-resource allocator 6.51–6.55

    If several processes are queued on x and x.signal() is executed, which one resumes? FCFS is frequently not adequate. Use the conditional-wait construct x.wait(c), where c is an integer priority number; the process with the lowest number (= highest priority) is scheduled next.

    Application: allocate a single resource among competing processes, using as priority number the maximum time a process plans to use the resource — the process with the shortest time gets the resource first. Access via an instance R of type ResourceAllocator:

    R.acquire(t);       // t = maximum time the process plans to use the resource
    ...
    access the resource;
    ...
R.release();
    monitor ResourceAllocator
{
    boolean busy;
    condition x;
    void acquire(int time) {
        if (busy)
            x.wait(time);   // queue ordered by time: shortest first
        busy = true;
    }
    void release() {
        busy = false;
        x.signal();         // wakes the waiter with the smallest time
    }
    initialization code() {
        busy = false;
    }
}

    Mini-trace: A holds the resource. B calls acquire(10), C calls acquire(3) → both wait; queue ordered C(3), B(10). A releases → x.signal() resumes C (smallest t), even though B came first.

    Incorrect use of monitor operations 6.55 — the monitor only protects its internal data; the caller must still use it correctly: release() … acquire(); acquire() … acquire(); omitting acquire() and/or release(). (Same family of errors as with semaphores.)

    6.14 Liveness: deadlock, starvation, priority inversion 6.56–6.58

    Processes may have to wait indefinitely while trying to acquire a synchronization tool (mutex lock, semaphore). Waiting indefinitely violates the progress and bounded-waiting criteria. Liveness = a set of properties a system must satisfy to ensure processes make progress; indefinite waiting is a liveness failure.

    Deadlock 6.57

    Deadlock — two or more processes are waiting indefinitely for an event that can be caused only by one of the waiting processes. Let S and Q be semaphores initialized to 1:

    // P0
wait(S);
wait(Q);
...
signal(S);
signal(Q);
    // P1
wait(Q);
wait(S);
...
signal(Q);
signal(S);

    If P0 executes wait(S) and then P1 executes wait(Q): when P0 executes wait(Q) it must wait until P1 executes signal(Q); but P1 is waiting until P0 executes signal(S). These signals will never be executed → P0 and P1 are deadlocked. (Note: if P0 had done both waits before P1 started, there would be no deadlock — deadlock depends on the interleaving.)

    Other liveness failures 6.58

    • Starvation — indefinite blocking: a process may never be removed from the semaphore queue in which it is suspended (e.g., the queue is served LIFO).
    • Priority inversion — a scheduling problem when a lower-priority process holds a lock needed by a higher-priority process. Solved via the priority-inheritance protocol: the lock holder temporarily inherits the higher priority until it releases the lock.

    Example of priority inversion: priorities L < M < H. L holds lock R; H requests R and waits; M (doesn't need R) preempts L. Now H effectively waits for M — a lower-priority process. With inheritance, L runs at H's priority, M can't preempt it, L releases R quickly, H proceeds.

    Chapter 6 review

    Summary

    • A race condition happens when the outcome depends on the interleaving of accesses to shared data. A critical section must satisfy mutual exclusion, progress, bounded waiting.
    • Interrupt disabling: only for short code on uniprocessors. Strict alternation (turn only) fails progress. Peterson (flag[2] + turn) satisfies all three — but only with no reordering; modern CPUs need memory barriers.
    • test_and_set and compare_and_swap are atomic hardware instructions; simple locks built from them give ME + progress but not bounded waiting; the waiting[] + cyclic hand-off algorithm adds bounded waiting (≤ n−1).
    • Atomic variables (built on CAS) make single updates atomic.
    • Mutex lock = acquire/release; busy-waiting version = spinlock.
    • Semaphore: integer + atomic wait/signal (P/V). Init 1 → mutual exclusion; init 0 → ordering; init n → n resources. Blocking implementation: decrement-then-test; negative value = number waiting.
    • Monitor: ADT with automatic mutual exclusion; condition variables x.wait()/x.signal() (signal is lost if nobody waits). Can be implemented with semaphores mutex, next, x_sem and counters. x.wait(c) = priority wait.
    • Liveness failures: deadlock, starvation, priority inversion (fix: priority inheritance).

    7.1 Bounded-Buffer (producer–consumer) problem 7.4–7.6

    Problem: a producer puts items into a shared buffer of n slots (each holds one item); a consumer removes them. The producer must wait when the buffer is full; the consumer must wait when it is empty; and buffer updates must not overlap.

    Shared semaphores — memorise the initial values
    • mutex = 1 — mutual exclusion on the buffer.
    • full = 0 — counts filled slots (items available to consume).
    • empty = n — counts empty slots (space available to produce).
    // Producer
while (true) {
    ...  /* produce an item in next_produced */
    wait(empty);     // 1. wait for a free slot
    wait(mutex);     // 2. lock buffer
    ...  /* add next_produced to the buffer */
    signal(mutex);   // 3. unlock
    signal(full);    // 4. one more full slot
}
    // Consumer
while (true) {
    wait(full);      // 1. wait for an item
    wait(mutex);     // 2. lock buffer
    ...  /* remove an item to next_consumed */
    signal(mutex);   // 3. unlock
    signal(empty);   // 4. one more empty slot
    ...  /* consume the item in next_consumed */
}

    The producer and consumer are mirror images: the producer waits on empty and signals full; the consumer waits on full and signals empty. Invariant: full + empty = n (when nobody is mid-operation).

    Why the order of the two waits matters

    Swap them in the producer — wait(mutex); wait(empty); — and let the buffer be full. The producer takes mutex, then blocks on empty while holding mutex. The consumer then blocks on wait(mutex) and can never free a slot → deadlock. Rule: wait on the counting semaphore first, then the mutex. (The order of the two signals does not cause deadlock.)

    7.2 Readers–Writers problem 7.7–7.11

    A data set is shared among concurrent processes: readers only read (no updates); writers can both read and write. Goal: allow multiple readers to read at the same time, but only a single writer may access the shared data at a time (and no readers while a writer writes). Several variations exist — all involve some form of priorities.

    Shared data
    • Data set
    • rw_mutex = 1 — writers' lock (also held by the readers as a group)
    • mutex = 1 — protects read_count
    • read_count = 0 — how many readers are currently reading
    // Writer
while (true) {
    wait(rw_mutex);
    ...  /* writing is performed */
    signal(rw_mutex);
}
    // Reader
while (true){
    wait(mutex);
    read_count++;
    if (read_count == 1)   /* first reader */
        wait(rw_mutex);     // lock writers out
    signal(mutex);
    ...  /* reading is performed */
    wait(mutex);
    read_count--;
    if (read_count == 0)   /* last reader */
        signal(rw_mutex);   // let writers in
    signal(mutex);
}

    Idea: readers act as one team. Only the first reader competes with writers for rw_mutex; only the last reader releases it. mutex just protects the counter.

    • First readers–writers problem — the solution above: readers never wait unless a writer already has the data. Can result in a writer that never writes (writer starvation).
    • Second readers–writers problem — once a writer is ready to write, no “newly arrived reader” is allowed to read (writer priority). Readers can starve.
    • Both may result in starvation, leading to even more variations. Some systems solve the problem with kernel-provided reader-writer locks.

    7.3 Dining-Philosophers problem 7.12–7.16

    N philosophers sit at a round table with a bowl of rice in the middle. They alternate thinking and eating, and do not interact with their neighbours. Occasionally one tries to pick up 2 chopsticks (one at a time) — the ones on its left and right — to eat; it needs both to eat, then releases both. For 5 philosophers the shared data is the bowl of rice (data set) and semaphore chopstick[5], all initialized to 1.

    Semaphore solution 7.13

    // structure of Philosopher i
while (true){
    wait (chopstick[i] );
    wait (chopstick[ (i + 1) % 5] );
        /* eat for awhile */
    signal (chopstick[i] );
    signal (chopstick[ (i + 1) % 5] );
        /* think for awhile */
}
    Slide question: “What is the problem with this algorithm?” — Answer

    It guarantees no two neighbours eat at once, but it can deadlock: if all five become hungry at the same moment and each executes wait(chopstick[i]), every chopstick value becomes 0; each then blocks forever on wait(chopstick[(i+1)%5]). Each holds one and waits for one held by its neighbour — a circular wait. (Common textbook remedies: allow at most 4 philosophers at the table; pick up both chopsticks only if both are available, inside a critical section; or an asymmetric order — odd philosophers pick left first, even pick right first.) Starvation is also possible.

    Monitor solution 7.14–7.16

    monitor DiningPhilosophers
{
    enum {THINKING, HUNGRY, EATING} state[5];
    condition self[5];

    void pickup(int i) {
        state[i] = HUNGRY;
        test(i);                          // try to start eating
        if (state[i] != EATING) self[i].wait;   // couldn't: sleep
    }
    void putdown(int i) {
        state[i] = THINKING;
        // test left and right neighbors
        test((i + 4) % 5);
        test((i + 1) % 5);
    }
    void test(int i) {
        if ((state[(i + 4) % 5] != EATING) &&   // left neighbour not eating
            (state[i] == HUNGRY) &&               // I am hungry
            (state[(i + 1) % 5] != EATING)) {      // right neighbour not eating
            state[i] = EATING;
            self[i].signal();
        }
    }
    initialization_code() {
        for (int i = 0; i < 5; i++)
            state[i] = THINKING;
    }
}
// Each philosopher i:
DiningPhilosophers.pickup(i);
    /** EAT **/
DiningPhilosophers.putdown(i);

    Key ideas: (i+4)%5 is the left neighbour (same as i−1 mod 5), (i+1)%5 the right. A philosopher picks up both chopsticks at once (only when neither neighbour is eating), so the hold-and-wait pattern behind the deadlock disappears. On putdown it tests both neighbours, which wakes a hungry neighbour that can now eat.

    7.4 Kernel synchronization — Windows 7.17–7.18

    • Uses interrupt masks to protect access to global resources on uniprocessor systems.
    • Uses spinlocks on multiprocessor systems; a spinlocking thread will never be preempted.
    • Provides dispatcher objects in user-land, which may act as mutexes, semaphores, events, and timers. Events act much like a condition variable. Timers notify one or more threads when time expired.
    • Dispatcher objects are either in the signaled state (object available) or non-signaled state (thread will block).

    • Linux provides: semaphores, atomic integers, spinlocks, and reader-writer versions of both.

    7.6 POSIX synchronization 7.21–7.27

    The POSIX API provides mutex locks, semaphores, and condition variables; widely used on UNIX, Linux, and macOS.

    POSIX mutex locks 7.22

    #include <pthread.h>
pthread_mutex_t mutex;
/* create and initialize the mutex lock */
pthread_mutex_init(&mutex,NULL);

/* acquire the mutex lock */
pthread_mutex_lock(&mutex);
/* critical section */
/* release the mutex lock */
pthread_mutex_unlock(&mutex);

    POSIX semaphores: named vs unnamed 7.23–7.25

    Two versions. Named semaphores can be used by unrelated processes; unnamed cannot (unnamed ones are shared by threads of a process or related processes).

    // NAMED
#include <semaphore.h>
sem_t *sem;
/* Create the semaphore and initialize it to 1 */
sem = sem_open("SEM", O_CREAT, 0666, 1);

/* acquire the semaphore */
sem_wait(sem);
/* critical section */
/* release the semaphore */
sem_post(sem);
    // UNNAMED
#include <semaphore.h>
sem_t sem;
/* Create the semaphore and initialize it to 1 */
sem_init(&sem, 0, 1);

/* acquire the semaphore */
sem_wait(&sem);
/* critical section */
/* release the semaphore */
sem_post(&sem);

    Spot the differences: named uses a pointer sem_t *sem returned by sem_open with a name "SEM" (another process accesses it by referring to the name SEM), flag O_CREAT, permissions 0666, initial value 1. Unnamed declares a sem_t object and calls sem_init(&sem, 0, 1) (second argument 0 = shared only among threads of this process; last = initial value 1). wait() ≙ sem_wait, signal() ≙ sem_post.

    POSIX condition variables 7.26–7.27

    C/C++ have no monitors, so a POSIX condition variable is associated with a POSIX mutex lock to provide mutual exclusion.

    pthread_mutex_t mutex;
pthread_cond_t cond_var;
pthread_mutex_init(&mutex,NULL);
pthread_cond_init(&cond_var,NULL);
    // Thread waiting for a == b
pthread_mutex_lock(&mutex);
while (a != b)
    pthread_cond_wait(&cond_var, &mutex);
pthread_mutex_unlock(&mutex);
    // Thread signaling
pthread_mutex_lock(&mutex);
a = b;
pthread_cond_signal(&cond_var);
pthread_mutex_unlock(&mutex);

    Important lines: pthread_cond_wait(&cond_var, &mutex) releases the mutex while waiting and re-acquires it before returning (that's why the mutex is passed). The test is in a while loop, not an if, so the condition is re-checked after waking (it may have changed again).

    7.7 Java synchronization 7.28–7.40

    Java provides: Java monitors, reentrant locks, semaphores, condition variables.

    Java monitors 7.29–7.33

    • Every Java object has a single lock associated with it.
    • If a method is declared synchronized, a calling thread must own the lock for the object.
    • If the lock is owned by another thread, the caller must wait until it is released; locks are released when the owning thread exits the synchronized method.
    When a thread calls wait() 7.32
    1. It releases the lock for the object.
    2. Its state is set to blocked.
    3. It is placed in the wait set for the object.

    A thread typically calls wait() when waiting for a condition to become true.

    When a thread calls notify() 7.33
    1. An arbitrary thread T is selected from the wait set.
    2. T is moved from the wait set to the entry set.
    3. T's state is set from blocked to runnable.

    T can now compete for the lock to check whether the condition it was waiting for is now true.

    Bounded buffer in Java 7.30, 7.34–7.35

    public class BoundedBuffer<E>
{
    private static final int BUFFER_SIZE = 5;
    private int count, in, out;
    private E[] buffer;

    public BoundedBuffer() {
        count = 0;
        in = 0;
        out = 0;
        buffer = (E[]) new Object[BUFFER_SIZE];
    }

    /* Producers call this method */
    public synchronized void insert(E item) {
        while (count == BUFFER_SIZE) {
            try {
                wait();
            }
            catch (InterruptedException ie) { }
        }
        buffer[in] = item;
        in = (in + 1) % BUFFER_SIZE;
        count++;
        notify();
    }

    /* Consumers call this method */
    public synchronized E remove() {
        E item;
        while (count == 0) {
            try {
                wait();
            }
            catch (InterruptedException ie) { }
        }
        item = buffer[out];
        out = (out + 1) % BUFFER_SIZE;
        count--;
        notify();
        return item;
    }
}

    How it maps to the semaphore version: synchronized replaces mutex; while(count == BUFFER_SIZE) wait() replaces wait(empty); while(count == 0) wait() replaces wait(full); notify() replaces the signal. in/out wrap around with % BUFFER_SIZE (circular buffer). The while loop re-checks the condition because a notified thread must re-compete for the lock.

    Reentrant locks 7.36

    Lock key = new ReentrantLock();
key.lock();
try {
    /* critical section */
}
finally {
    key.unlock();
}

    Similar to mutex locks. The finally clause ensures the lock is released even if an exception occurs in the try block. (“Reentrant” = the owning thread may lock it again without deadlocking itself.)

    Java semaphores 7.37

    // Constructor:

    sem.acquire();

    acquire() ≙ wait(), release() ≙ signal().

    Java condition variables 7.38–7.40

    Condition variables are associated with a ReentrantLock, created with its newCondition() method. A thread waits with await() and signals with signal().

    Lock key = new ReentrantLock();
Condition condVar = key.newCondition();

    Example: five threads numbered 0..4; shared variable turn indicates whose turn it is. A thread calls doWork() when it wishes to do work, but may only work on its turn: if not its turn, wait; if its turn, work for a while; when done, notify the thread whose turn is next.

    // Necessary data structures
Lock lock = new ReentrantLock();
Condition[] condVars = new Condition[5];
for (int i = 0; i < 5; i++)
    condVars[i] = lock.newCondition();

/* threadNumber is the thread that wishes to do some work */
public void doWork(int threadNumber)
{
    lock.lock();
    try {
        /**
         * If it's not my turn, then wait
         * until I'm signaled.
         */
        if (threadNumber != turn)
            condVars[threadNumber].await();
        /**
         * Do some work for awhile ...
         */
        /**
         * Now signal to the next thread.
         */
        turn = (turn + 1) % 5;
        condVars[turn].signal();
    }
    catch (InterruptedException ie) { }
    finally {
        lock.unlock();
    }
}

    Why one condition per thread: signal() on condVars[turn] wakes exactly the thread whose turn it is, instead of waking an arbitrary waiter (as Java's single notify() would). Trace: turn = 0; thread 2 calls doWork → 2 ≠ 0 → awaits on condVars[2]. Thread 0 works, sets turn = 1, signals condVars[1]. Thread 1 works, sets turn = 2, signals condVars[2] → thread 2 wakes and works.

    7.8 Alternative approaches 7.41–7.44

    Transactional memory

    Consider update() that must run atomically. With mutex locks:

    void update ()
{
    acquire();
    /* modify shared data */
    release();
}

    A memory transaction is a sequence of read-write operations to memory that are performed atomically. Adding atomic{S} ensures the statements in S execute atomically:

    void update ()
{
    atomic {
        /* modify shared data */
    }
}

    The system, not the programmer, guarantees atomicity — no locks to forget or deadlock on.

    OpenMP

    A set of compiler directives and an API supporting parallel programming.

    void update(int value)
{
    #pragma omp critical
    {
        count += value
    }
}

    Code inside #pragma omp critical is treated as a critical section and performed atomically.

    Functional programming languages

    Offer a different paradigm from procedural languages: they do not maintain state. Variables are immutable — they cannot change once assigned. Since nothing shared is ever modified, data races cannot occur. Increasing interest in Erlang and Scala for this reason.

    • Java: synchronized methods with an object lock, entry set and wait set, wait()/notify(); ReentrantLock with finally; Semaphore acquire/release; Condition await/signal.
    • Alternatives: transactional memory (atomic{S}), OpenMP (#pragma omp critical), functional languages (immutable state).

    Chapter 8 — Deadlocks

    Big picture. Chapter 6 showed a deadlock between two semaphores. This chapter studies deadlock systematically: what conditions cause it, how to draw it (resource-allocation graphs), and the three strategies: prevent it (break a necessary condition), avoid it (Banker's algorithm keeps the system in a safe state), or detect and recover. 8.2–8.3

    Objectives (8.3): illustrate deadlock with mutex locks; define the four necessary conditions; identify deadlock in a resource-allocation graph; evaluate the four prevention approaches; apply the banker's algorithm; apply the detection algorithm; evaluate recovery approaches.

    8.1 System model and a first deadlock 8.4–8.5

    • A system consists of resources of types R1, R2, …, Rm (CPU cycles, memory space, I/O devices).
    • Each resource type Ri has Wi instances (identical copies; any instance satisfies a request for that type).
    • Each process/thread uses a resource in the order: request → use → release.

    Deadlock with semaphores: semaphores S1 and S2 both initialized to 1; two threads:

    // T1
wait(s1)
wait(s2)
    // T2
wait(s2)
wait(s1)

    If T1 does wait(s1) and T2 does wait(s2) before either's second wait, each holds one semaphore and waits forever for the other's → deadlock.

    8.2 Deadlock characterization — four necessary conditions 8.6

    Deadlock can arise if all four conditions hold simultaneously:

    1. Mutual exclusion: only one thread at a time can use a resource.
    2. Hold and wait: a thread holding at least one resource is waiting to acquire additional resources held by other threads.
    3. No preemption: a resource can be released only voluntarily by the thread holding it, after that thread has completed its task.
    4. Circular wait: there exists a set {T0, T1, …, Tn} of waiting threads such that T0 waits for a resource held by T1, T1 waits for one held by T2, …, Tn−1 waits for one held by Tn, and Tn waits for one held by T0.
    Exam trap

    These are necessary, not sufficient, conditions in general: all four must hold for a deadlock, so breaking any one makes deadlock impossible. (With single-instance resources, a circular wait does mean deadlock — see the basic facts below.) Mnemonic: M-H-N-C (“My House Needs Cleaning”).

    8.3 Resource-allocation graph (RAG) 8.7–8.11

    A RAG has a set of vertices V and a set of edges E. V is partitioned into T = {T1, …, Tn} (all threads, drawn as circles) and R = {R1, …, Rm} (all resource types, drawn as rectangles with one dot per instance).

    • Request edge — directed edge Ti → Rj (thread is waiting for the resource; points to the box).
    • Assignment edge — directed edge Rj → Ti (an instance is held by the thread; starts at a dot).
    Basic facts 8.11 — memorise
    • Graph contains no cycles ⇒ no deadlock.
    • Graph contains a cycle ⇒ if only one instance per resource type, then deadlock; if several instances per resource type, possibility of deadlock.

    8.4 Methods for handling deadlocks 8.12

    1. Ensure the system will never enter a deadlock state: deadlock prevention or deadlock avoidance.
    2. Allow the system to enter a deadlock state and then recover (detection + recovery).
    3. Ignore the problem and pretend deadlocks never occur in the system (what most general-purpose OSes, e.g. Linux and Windows, do in practice).
    Prevention vs avoidance — how to tell them apart

    Prevention = a static design rule that makes one of the 4 conditions impossible (e.g., “always lock in increasing order”). No run-time knowledge needed. Avoidance = a run-time decision on each request using advance knowledge of maximum needs (“granting this would make the state unsafe, so wait”). If a question mentions Max/claims/safe state → avoidance.

    8.5 Deadlock prevention 8.13–8.15

    Invalidate one of the four necessary conditions:

    ConditionHow to break itCost / limitation
    Mutual exclusionNot required for sharable resources (e.g., read-only files).Must hold for non-sharable resources, so generally cannot be broken.
    Hold and waitGuarantee that whenever a thread requests a resource, it does not hold any others: require threads to request and be allocated all resources before execution, or allow a request only when the thread has none allocated.Low resource utilization; starvation possible.
    No preemptionIf a process holding some resources requests another that cannot be immediately allocated, all resources currently held are released (preempted). Preempted resources are added to the list it is waiting for. The thread restarts only when it can regain its old resources and the new ones.Only for resources whose state can be saved/restored (CPU registers, memory), not e.g. locks or printers.
    Circular waitImpose a total ordering of all resource types and require each thread to request resources in increasing order of enumeration.Most common approach in practice.

    Circular wait in practice 8.15

    Assign each resource (i.e., mutex lock) a unique number; locks must be acquired in order. If first_mutex = 1 and second_mutex = 5, then the code for thread_two could not be written as follows:

    /* thread_one runs in this function */
void *do_work_one(void *param)
{
    pthread_mutex_lock(&first_mutex);
    pthread_mutex_lock(&second_mutex);
    /**
     * Do some work
     */
    pthread_mutex_unlock(&second_mutex);
    pthread_mutex_unlock(&first_mutex);
    pthread_exit(0);
}
    /* thread_two runs in this function */
void *do_work_two(void *param)
{
    pthread_mutex_lock(&second_mutex);  // 5 first — ILLEGAL
    pthread_mutex_lock(&first_mutex);   // then 1
    /**
     * Do some work
     */
    pthread_mutex_unlock(&first_mutex);
    pthread_mutex_unlock(&second_mutex);
    pthread_exit(0);
}

    Why: thread_two acquires lock 5 and then lock 1 — a decreasing order. That's exactly what allows thread_one (holding 1, wanting 5) and thread_two (holding 5, wanting 1) to wait on each other. If both must lock 1 before 5, a cycle can never form: whoever holds 5 already holds 1.

    8.6 Deadlock avoidance and safe states 8.16–8.19

    • The simplest and most useful model requires each thread to declare the maximum number of resources of each type that it may need.
    • The avoidance algorithm dynamically examines the resource-allocation state to ensure there can never be a circular-wait condition.
    • Resource-allocation state = number of available and allocated resources, and the maximum demands of the processes.
    • Requires that the system has some additional a priori information available.
    Safe state 8.17

    When a thread requests an available resource, the system must decide whether immediate allocation leaves the system in a safe state.

    The system is in a safe state if there exists a sequence <T1, T2, …, Tn> of ALL the threads such that, for each Ti, the resources Ti can still request can be satisfied by currently available resources + resources held by all Tj with j < i. That is:

    • If Ti's needs are not immediately available, Ti can wait until all Tj have finished.
    • When Tj finishes, Ti can obtain its needed resources, execute, return its allocated resources, and terminate.
    • When Ti terminates, Ti+1 can obtain its needed resources, and so on.
    Basic facts 8.18
    • Safe state ⇒ no deadlocks.
    • Unsafe state ⇒ possibility of deadlock.
    • Avoidance ⇒ ensure the system never enters an unsafe state.
    Exam trap

    “Unsafe” does not mean “deadlocked”. Unsafe only means the OS can no longer guarantee that every thread finishes; it depends on what the threads request next.

    Avoidance algorithms 8.20: single instance of each resource type → use a resource-allocation graph; multiple instances → use the Banker's Algorithm.

    8.7 Resource-allocation-graph avoidance scheme 8.21–8.24

    • Claim edge Ti ⇢ Rj: thread Ti may request resource Rj in the future; drawn as a dashed line.
    • A claim edge converts to a request edge when the thread requests the resource.
    • A request edge converts to an assignment edge when the resource is allocated.
    • When a thread releases a resource, the assignment edge reconverts to a claim edge.
    • Resources must be claimed a priori in the system.

    Slide 8.21 reads “Claim edge Ti → Rj indicated that process Tj may request resource Rj” — it should say Ti.

    The algorithm 8.24

    Suppose Ti requests Rj. The request can be granted only if converting the request edge to an assignment edge does not result in a cycle in the resource-allocation graph (claim edges included). Applied to 8.22: if T2 requests R2, granting it yields graph 8.23, which has a cycle → T2 must wait, even though R2 is free.

    8.8 Banker's Algorithm 8.25–8.31

    Used for multiple instances of resources. Rules: each thread must a priori claim maximum use; when a thread requests a resource it may have to wait; when a thread gets all its resources it must return them in a finite amount of time. (Name: a banker never lends money if it could end up unable to satisfy all customers.)

    Data structures 8.26 — n = number of processes, m = number of resource types
    • Available: vector of length m. Available[j] = k ⇒ k instances of Rj available.
    • Max: n × m matrix. Max[i,j] = k ⇒ Ti may request at most k instances of Rj.
    • Allocation: n × m matrix. Allocation[i,j] = k ⇒ Ti currently holds k instances of Rj.
    • Need: n × m matrix. Need[i,j] = k ⇒ Ti may need k more instances of Rj to complete.
      Need[i,j] = Max[i,j] − Allocation[i,j]

    Notation: Allocationi, Needi, Requesti are row i (a vector). X ≤ Y means X[j] ≤ Y[j] for every j.

    Safety algorithm 8.27

    1 Let Work and Finish be vectors of length m and n.  Initialize:
      Work = Available
      Finish[i] = false   for i = 0, 1, …, n-1
2 Find an i such that both:
      (a) Finish[i] == false
      (b) Needi ≤ Work
   If no such i exists, go to step 4
3 Work = Work + Allocationi
   Finish[i] = true
   go to step 2
4 If Finish[i] == true for all i, the system is in a safe state

    Intuition: Work = resources free if we let the threads chosen so far run to completion. Step 2 picks a thread whose remaining need fits; step 3 pretends it finishes and returns its Allocation (not its Max, not its Need). The order in which threads get Finish = true is a safe sequence.

    Resource-request algorithm for Ti 8.28

    Requesti = request vector for Ti; Requesti[j] = k ⇒ Ti wants k instances of Rj
1 If Requesti ≤ Needi go to step 2.
   Otherwise raise error condition (process has exceeded its maximum claim).
2 If Requesti ≤ Available go to step 3.
   Otherwise Ti must wait (resources are not available).
3 Pretend to allocate the requested resources to Ti:
      Available    = Available    − Requesti;
      Allocationi = Allocationi + Requesti;
      Needi       = Needi       − Requesti;
   Run the safety algorithm on this new state:
      If safe   ⇒ the resources are allocated to Ti
      If unsafe ⇒ Ti must wait, and the old resource-allocation state is restored
    Order of checks — don't mix them up
    1. Request ≤ Need? No → error (lying about max).
    2. Request ≤ Available? No → wait (not enough now).
    3. Pretend + safety. Unsafe → wait and roll back.

    Three different outcomes: error, wait (not available), wait (unsafe). Only “safe” grants.

    8.9 Deadlock detection 8.32–8.39

    Allow the system to enter a deadlock state, then use a detection algorithm and a recovery scheme.

    Single instance of each resource type: wait-for graph 8.33–8.34

    • Maintain a wait-for graph: nodes are threads; Ti → Tj if Ti is waiting for Tj.
    • Periodically invoke an algorithm that searches for a cycle; if there is a cycle, there exists a deadlock.
    • Detecting a cycle requires on the order of n2 operations, where n = number of vertices.
    • Construction: remove the resource nodes and collapse edges: Ti → Rq → Tj becomes Ti → Tj.

    Several instances of a resource type 8.35–8.37

    • Available: vector of length m — available instances of each type.
    • Allocation: n × m matrix — resources of each type currently allocated to each thread.
    • Request: n × m matrix — the current request of each thread. Request[i][j] = k ⇒ Ti is requesting k more instances of Rj.
    1 Let Work and Finish be vectors of length m and n.  Initialize:
      Work = Available
      For i = 1,2,…,n: if Allocationi ≠ 0 then Finish[i] = false; otherwise Finish[i] = true
2 Find an index i such that both:
      Finish[i] == false
      Requesti ≤ Work
   If no such i exists, go to step 4
3 Work = Work + Allocationi
   Finish[i] = true
   go to step 2
4 If Finish[i] == false for some i, 1 ≤ i ≤ n, then the system is in a deadlock state.
   Moreover, if Finish[i] == false, then Ti is deadlocked.

    Complexity: on the order of O(m × n2) operations.

    Detection vs Banker's safety algorithm — the 3 differences
    1. Detection uses Request (what is asked now); safety uses Need (worst-case future).
    2. Detection initializes Finish[i] = true if Allocationi = 0 (a thread holding nothing can't be part of a deadlock); safety sets all to false.
    3. Result meaning: detection's leftover false = actually deadlocked threads; safety's leftover false = unsafe (maybe deadlock).

    Detection is optimistic: it assumes a thread whose current request can be met will finish and release everything.

    Detection-algorithm usage 8.40

    When, and how often, to invoke it depends on: how often a deadlock is likely to occur, and how many processes will need to be rolled back (one for each disjoint cycle). If detection is invoked arbitrarily (rarely), there may be many cycles in the graph and we would not be able to tell which of the many deadlocked threads “caused” the deadlock. (Invoking it on every request that can't be granted immediately finds the culprit but costs a lot of overhead.)

    8.10 Recovery from deadlock 8.41–8.42

    Process termination

    • Abort all deadlocked threads (simple, expensive — lots of lost work), or
    • Abort one process at a time until the deadlock cycle is eliminated (re-run detection after each abort).

    In which order to abort? Consider:

    1. Priority of the thread
    2. How long it has computed, and how much longer to completion
    3. Resources the thread has used
    4. Resources the thread needs to complete
    5. How many threads will need to be terminated
    6. Is the thread interactive or batch?

    Resource preemption

    • Selecting a victim — minimize cost.
    • Rollback — return to some safe state, restart the thread from that state.
    • Starvation — the same thread may always be picked as victim; fix: include the number of rollbacks in the cost factor.

    Chapter 8 review

    Summary

    • Deadlock requires mutual exclusion, hold and wait, no preemption, circular wait simultaneously.
    • RAG: request edge T→R, assignment edge R→T, claim edge T⇢R (dashed, avoidance). No cycle ⇒ no deadlock. Cycle + single instances ⇒ deadlock; cycle + multiple instances ⇒ possible deadlock.
    • Strategies: prevention (break a condition — circular wait via lock ordering is most common), avoidance (safe states; RAG algorithm for single instances, Banker's for multiple), detection + recovery, or ignore.
    • Safe ⇒ no deadlock; unsafe ⇒ possible deadlock; deadlock ⊂ unsafe.
    • Banker's: Need = Max − Allocation. Request: ≤ Need (else error) → ≤ Available (else wait) → pretend and run safety (unsafe → wait + restore).
    • Detection: wait-for graph (single instance, O(n²)) or Available/Allocation/Request algorithm (O(m×n²)); Finish starts true for threads holding nothing.
    • Recovery: terminate (all / one at a time, ordered by cost factors) or preempt (victim, rollback, avoid starvation by counting rollbacks).

The OS + hardware must (1) protect processes from each other, (2) let programs use addresses that don't depend on where they're loaded (logical → physical translation), and (3) allocate memory efficiently. The chapter moves from contiguous allocation (base/limit registers, holes, fragmentation) to paging (page tables, TLB, hierarchical/hashed/inverted tables), then swapping and real hardware (Intel IA-32/x86-64, ARM). 9.2–9.3

    Objectives (9.3): describe ways of organizing memory hardware; discuss memory-management techniques; describe the Intel Pentium, which supports both pure segmentation and segmentation with paging.

    9.1 Background 9.4

    • A program must be brought (from disk) into memory and placed within a process to run.
    • Main memory and registers are the only storage the CPU can access directly.
    • The memory unit only sees a stream of addresses + read requests, or address + data and write requests — it doesn't know what the address means.
    • Register access: one CPU clock (or less). Main memory: many cycles, causing a stall. A cache sits between main memory and CPU registers to reduce this.
    • Protection of memory is required to ensure correct operation.

    9.2 Protection with base and limit registers 9.5–9.6

    We must ensure a process can access only addresses in its address space. A pair of base and limit registers define the logical address space of a process: base = smallest legal physical address; limit = size of the range. Legal addresses: base ≤ address < base + limit.

    Mini example (9.5 numbers): base = 300040, limit = 120900. Address 420940 → 420940 < 420940? No → trap. Address 300039 → ≥ 300040? No → trap. Address 356000 → legal.

    9.3 Address binding 9.7–9.9

    Programs on disk, ready to be brought into memory to execute, form an input queue. Without support, a program must be loaded at address 0000 — inconvenient to have the first user process always at physical address 0000. Addresses are represented differently at each stage of a program's life:

    • Source code addresses are usually symbolic (e.g., variable count).
    • Compiled code addresses bind to relocatable addresses, e.g., “14 bytes from beginning of this module”.
    • The linker or loader binds relocatable addresses to absolute addresses, e.g., 74014.
    • Each binding maps one address space to another.
    Three binding times 9.8
    • Compile time: if the memory location is known a priori, absolute code can be generated; must recompile if the starting location changes.
    • Load time: must generate relocatable code if the memory location is not known at compile time.
    • Execution time: binding delayed until run time if the process can be moved during execution from one memory segment to another. Needs hardware support for address maps (e.g., base and limit registers).

    9.4 Logical vs physical addresses, MMU, relocation register 9.10–9.13

    Definitions
    • Logical address — generated by the CPU; also called virtual address.
    • Physical address — the address seen by the memory unit.
    • Logical and physical addresses are the same in compile-time and load-time binding; they differ in execution-time binding.
    • Logical address space = set of all logical addresses generated by a program; physical address space = set of all physical addresses corresponding to them. (Slide 9.10 literally says “physical addresses generated by a program”.)
    • MMU (memory-management unit) — hardware device that, at run time, maps virtual to physical addresses. Many methods possible (rest of the chapter).

    Simple MMU scheme 9.12–9.13: a generalization of the base-register scheme. The base register is now called the relocation register. The value in the relocation register is added to every address generated by a user process at the time it is sent to memory. The user program deals with logical addresses and never sees the real physical addresses; execution-time binding occurs when a reference is made to a memory location.

    9.5 Dynamic loading and dynamic linking 9.14–9.15

    Dynamic loading
    • The entire program does not need to be in memory to execute. (Slide 9.14 says “does need” — a typo for “does not need”.)
    • A routine is not loaded until it is called → better memory-space utilization; an unused routine is never loaded.
    • All routines kept on disk in relocatable load format.
    • Useful when large amounts of code handle infrequently occurring cases (e.g., error routines).
    • No special support from the OS required — implemented through program design; the OS can help by providing libraries.
    Dynamic linking
    • Static linking — system libraries and program code combined by the loader into the binary program image.
    • Dynamic linking — linking postponed until execution time.
    • A small piece of code, the stub, locates the appropriate memory-resident library routine; the stub replaces itself with the address of the routine and executes it.
    • The OS checks if the routine is in the process's memory address space; if not, adds it.
    • Particularly useful for libraries; system also known as shared libraries.
    • Consider applicability to patching system libraries (update the library once, all programs use the new version) — versioning may be needed.
    Dynamic loading vs dynamic linking

    Loading = when a routine's code is brought into memory (on first call; the programmer arranges it). Linking = when a library reference is resolved (at run time via a stub; needs OS help since the library may be shared among processes).

    9.6 Contiguous allocation 9.16–9.18

    Main memory must support both the OS and user processes; it's a limited resource, so it must be allocated efficiently. Contiguous allocation is an early method. Memory is usually split into two partitions: the resident OS, usually in low memory with the interrupt vector, and user processes in high memory. Each process is contained in a single contiguous section of memory.

    Relocation registers protect user processes from each other and from changing OS code and data:

    • Base (relocation) register contains the value of the smallest physical address.
    • Limit register contains the range of logical addresses — each logical address must be less than the limit register.
    • The MMU maps logical addresses dynamically — this allows actions such as kernel code being transient and the kernel changing size.
    Two protection schemes — don't mix them up

    9.6 (base & limit): the CPU address is already physical; check base ≤ addr < base+limit.
    9.18 (relocation & limit): the CPU address is logical (starts at 0); check logical < limit first, then physical = relocation + logical.
    Example: relocation = 14000, limit = 500. Logical 346 → 346 < 500 ✓ → 14346. Logical 600 → trap (never added).

    9.7 Variable partitions and dynamic storage allocation 9.19–9.20

    • Multiple-partition allocation: degree of multiprogramming limited by the number of partitions.
    • Variable-partition sizes for efficiency (sized to a given process's needs).
    • Hole — block of available memory; holes of various sizes are scattered throughout memory.
    • When a process arrives, it is allocated memory from a hole large enough to accommodate it.
    • A process exiting frees its partition; adjacent free partitions are combined.
    • The OS maintains information about: a) allocated partitions, b) free partitions (holes).
    How to satisfy a request of size n from a list of free holes 9.20
    • First-fit: allocate the first hole that is big enough.
    • Best-fit: allocate the smallest hole that is big enough; must search the entire list unless ordered by size. Produces the smallest leftover hole.
    • Worst-fit: allocate the largest hole; must also search the entire list. Produces the largest leftover hole.

    First-fit and best-fit are better than worst-fit in terms of speed and storage utilization.

    9.8 Fragmentation and compaction 9.21–9.22

    Two kinds
    • External fragmentation — total memory space exists to satisfy a request, but it is not contiguous (scattered between allocations).
    • Internal fragmentation — allocated memory may be slightly larger than requested; the difference is memory internal to a partition but not being used.

    50-percent rule: first-fit analysis reveals that given N blocks allocated, 0.5 N blocks are lost to fragmentation. So of N + 0.5N = 1.5N blocks, 0.5N/1.5N = 1/3 may be unusable.

    Compaction reduces external fragmentation: shuffle memory contents to place all free memory together in one large block.

    • Possible only if relocation is dynamic and done at execution time (moving a process means changing its relocation register).
    • I/O problem: a process doing I/O can't be moved (the device writes to fixed physical addresses). Solutions: latch the job in memory while it is involved in I/O, or do I/O only into OS buffers.
    • The backing store (disk) has the same fragmentation problems.

    9.9 Paging 9.23–9.27

    Paging lets the physical address space of a process be noncontiguous; a process is allocated physical memory wherever it is available. It avoids external fragmentation and the problem of varying-sized memory chunks.

    • Divide physical memory into fixed-sized blocks called frames. Size is a power of 2, between 512 bytes and 16 MB.
    • Divide logical memory into blocks of the same size called pages.
    • Keep track of all free frames. To run a program of size N pages, find N free frames and load the program.
    • Set up a page table to translate logical to physical addresses. The backing store is likewise split into pages.
    • Still have internal fragmentation (last page partly empty).

    Address translation scheme 9.24

    The CPU's address is divided into:

    • Page number (p) — index into the page table, which contains the base address of each page in physical memory (i.e., its frame number).
    • Page offset (d) — combined with that base address to define the physical address sent to the memory unit.
    Translation formulas (use whichever matches the question's format)

    p = ⌊ logical / page_size ⌋ d = logical mod page_size f = page_table[p] physical = f × page_size + d

    In binary/hex, this is just splitting bits: replace the p bits by the f bits, keep d unchanged.

    Recipe for any paging translation problem
    1. Find page size → n = log2(page size) offset bits.

    9.10 Calculating internal fragmentation; free frames 9.28–9.29

    Slide example: page size = 2,048 bytes; process size = 72,766 bytes.

    1. Divide: 72,766 ÷ 2,048 = 35 remainder ? → 35 × 2,048 = 71,680; 72,766 − 71,680 = 1,086. So the process is 35 pages + 1,086 bytes.
    2. It needs 36 frames (the 36th holds only 1,086 bytes).
    3. Internal fragmentation = 2,048 − 1,086 = 962 bytes.
    • Worst case fragmentation = 1 frame − 1 byte (process needs n pages + 1 byte → 2,047 bytes wasted here).
    • On average fragmentation = ½ frame size.
    • So are small frame sizes desirable? Less internal fragmentation, but each page-table entry takes memory to track (more pages → bigger page table). Page sizes are growing over time; e.g., Solaris supports two page sizes — 8 KB and 4 MB.
    Edge case

    If the process size is an exact multiple of the page size (remainder 0), internal fragmentation is 0, not a full page.

    9.11 Implementing the page table; TLB; effective access time 9.30–9.34

    • The page table is kept in main memory. Page-table base register (PTBR) points to the page table; page-table length register (PTLR) indicates its size.
    • In this scheme every data/instruction access requires two memory accesses: one for the page table and one for the data/instruction.
    • The two-memory-access problem is solved by a special fast-lookup hardware cache: the translation look-aside buffer (TLB), also called associative memory.
    TLB facts 9.31–9.32
    • Some TLBs store address-space identifiers (ASIDs) in each entry — uniquely identify each process to provide address-space protection. Otherwise the TLB must be flushed at every context switch.
    • TLBs are typically small: 64 to 1,024 entries.
    • On a TLB miss, the value is loaded into the TLB for faster access next time; replacement policies must be considered; some entries can be wired down for permanent fast access.
    • Associative memory = parallel search of all (Page #, Frame #) pairs at once. For address translation (p, d): if p is in an associative register, get frame # out; otherwise get frame # from the page table in memory.

    Effective access time (EAT) 9.34

    • TLB hit → mapped-memory access takes 10 ns (1 memory access).
    • TLB miss → two memory accesses → 20 ns. (The slide ignores the TLB search time.)

    9.12 Memory protection: protection bits and the valid–invalid bit 9.35–9.36

    • Protection bit associated with each frame to indicate read-only or read-write access; more bits can indicate execute-only, etc.
    • Valid–invalid bit attached to each page-table entry: “valid” = the page is in the process's logical address space (a legal page); “invalid” = it is not. Alternatively use the PTLR.
    • Any violation results in a trap to the kernel.

    9.13 Shared pages 9.37–9.38

    • Shared code: one copy of read-only (reentrant) code shared among processes (e.g., text editors, compilers, window systems). Similar to multiple threads sharing the same process space. Also useful for interprocess communication if sharing of read-write pages is allowed.
    • Private code and data: each process keeps a separate copy; these pages can appear anywhere in the logical address space.

    9.14 Structure of the page table: size problem and hierarchical paging 9.39–9.44

    Straightforward page tables can get huge. Slide calculation:

    1. 32-bit logical address space → 232 bytes.
    2. Page size 4 KB = 212 bytes.
    3. Number of entries = 232 / 212 = 220 ≈ 1 million entries.
    4. Each entry 4 bytes → 220 × 4 = 222 bytes = 4 MB of page table per process.

    We don't want to allocate that contiguously in main memory. Simple solution: divide the page table into smaller units — hierarchical paging, hashed page tables, inverted page tables.

    Hierarchical (multi-level) page tables

    Break the logical address space into multiple page tables. Simplest: a two-level page table — we page the page table.

    Two-level paging example 9.41–9.42

    32-bit machine, 4 KB pages: logical address = 20-bit page number + 12-bit offset. Since the page table is paged, the page number is further divided into a 10-bit page number and a 10-bit page offset:

    Worked two-level translation (fresh numbers)

    Logical address 0x00403A7C, 10/10/12 split.

    1. d = low 12 bits = last 3 hex digits = 0xA7C (= 2684).
    2. Page number = top 20 bits = 0x00403 = 0000 0000 0100 0000 00112 = 1027.
    3. p1 = top 10 of those = 00000000012 = 1; p2 = low 10 = 00000000112 = 3. (Check: 1 × 1024 + 3 = 1027 ✓.)
    4. Look up outer[1] → inner table page; inner[3] → frame, e.g. 0x2B5 → physical = 0x2B5 × 0x1000 + 0xA7C = 0x2B5A7C.

    Decimal method: p1 = ⌊LA / 222⌋, p2 = ⌊LA / 212⌋ mod 210, d = LA mod 212.

    64-bit logical address space 9.43–9.44

    Even two-level paging is not sufficient. With 4 KB pages (212):

    • Page table would have 264/212 = 252 entries.
    • Two-level scheme: inner page tables could be 210 4-byte entries (exactly one 4 KB page). Address: outer page p1 = 42 bits, inner page p2 = 10, offset d = 12.
    • Outer page table then has 242 entries or 242 × 4 = 244 bytes (16 TB!).

    9.15 Hashed page tables 9.45–9.46

    • Common in address spaces > 32 bits.
    • The virtual page number is hashed into a page table; each slot contains a chain of elements hashing to the same location.
    • Each element has: (1) the virtual page number, (2) the value of the mapped page frame, (3) a pointer to the next element.
    • Virtual page numbers in the chain are compared, searching for a match; if found, the corresponding physical frame is extracted.
    • Variation for 64-bit: clustered page tables — similar to hashed but each entry refers to several pages (such as 16) rather than 1; especially useful for sparse address spaces (memory references non-contiguous and scattered).

    9.16 Inverted page tables 9.47–9.48

    • Rather than each process having a page table tracking all possible logical pages, track all physical pages: one entry for each real page (frame) of memory.
    • Entry = the virtual address of the page stored in that real memory location, with information about the process that owns that page (pid).
    • Decreases memory needed to store page tables, but increases time to search the table on each reference.
    • Use a hash table to limit the search to one — or at most a few — entries; the TLB can accelerate access.
    • Shared memory is hard: there is only one mapping of a virtual address to the shared physical address (one entry per frame).
    Regular vs hashed vs inverted

    Regular: one table per process, indexed by page number, size ∝ logical space. Hashed: per-process (or system) hash on virtual page number; chain search. Inverted: one table for the whole system, one entry per frame, size ∝ physical memory; lookup by searching for (pid, p) — the index found is the frame number.

    9.17 Example: Oracle SPARC Solaris 9.49–9.50

    • A modern 64-bit OS with tightly integrated hardware; goals: efficiency, low overhead.
    • Based on hashing, but more complex: two hash tables — one for the kernel and one for all user processes. Each maps virtual to physical memory.
    • Each entry represents a contiguous area of mapped virtual memory — more efficient than one entry per page. Each entry has a base address and a span (number of pages the entry represents).
    • TLB holds translation table entries (TTEs) for fast hardware lookups. A cache of TTEs resides in a translation storage buffer (TSB), which includes an entry per recently accessed page.

    Lookup order: virtual address → TLB search → on miss, hardware walks the in-memory TSB for the TTE → if found, CPU copies the TSB entry into the TLB and translation completes → if not found, the kernel is interrupted to search the hash table; it creates a TTE from the hash table, stores it in the TSB, and the interrupt handler returns control to the MMU, which completes the translation.

    9.18 Swapping 9.51–9.57

    • A process can be swapped temporarily out of memory to a backing store, then brought back in for continued execution. Total physical memory space of processes can exceed physical memory.
    • Backing store — fast disk large enough for copies of all memory images for all users; must provide direct access to these images.
    • Roll out, roll in — swapping variant for priority-based scheduling: a lower-priority process is swapped out so a higher-priority process can be loaded and executed.
    • Major part of swap time is transfer time; total transfer time is directly proportional to the amount of memory swapped.
    • The system maintains a ready queue of ready-to-run processes which have memory images on disk.
    • Does a swapped-out process need to come back to the same physical addresses? Depends on the address-binding method (compile/load-time binding → yes; execution-time → no). Also consider pending I/O to/from the process's memory space.
    • Modified swapping is found on many systems (UNIX, Linux, Windows): swapping normally disabled; started if more than a threshold amount of memory is allocated; disabled again once demand falls below the threshold.

    Context-switch time including swapping 9.54–9.55

    If the next process to run is not in memory, we must swap out a process and swap in the target — context-switch time can be very high. Slide example: 100 MB process, hard disk transfer rate 50 MB/sec.

    1. Swap out time = size / rate = 100 MB ÷ 50 MB/s = 2 s = 2000 ms.
    2. Plus swap in of a same-sized process = 2000 ms.
    3. Total swapping component of the context switch = 4000 ms (4 seconds).

    swap time = 2 × (process size / transfer rate) (out + in, same size, ignoring latency)

    • Can reduce by reducing the amount of memory swapped — by knowing how much memory is really used: system calls request_memory() and release_memory() inform the OS.
    • Pending I/O: can't swap out, since I/O would occur to the wrong process. Or always transfer I/O to kernel space, then to the I/O device — known as double buffering, which adds overhead.
    • Standard swapping is not used in modern OSes, but a modified version is common: swap only when free memory is extremely low.

    Swapping on mobile systems 9.56

    Not typically supported: storage is flash memory — small amount of space, limited number of write cycles, poor throughput between flash and CPU. Instead, other methods free memory when low: iOS asks apps to voluntarily relinquish allocated memory (read-only data thrown out and reloaded from flash if needed; failure to free can result in termination). Android terminates apps if free memory is low, but first writes application state to flash for fast restart. Both support paging.

    9.19 Example: Intel 32- and 64-bit architectures 9.58–9.65

    Dominant industry chips. Pentium CPUs are 32-bit (IA-32); current Intel CPUs are 64-bit (slides call it IA-64; in practice this is the x86-64 architecture, slide 9.65). Many variations; main ideas only.

    IA-32 segmentation 9.59–9.62

    • Supports both segmentation and segmentation with paging.
    • Each segment can be 4 GB; up to 16 K segments per process, divided into two partitions:
      • First partition of up to 8 K segments private to the process — kept in the local descriptor table (LDT).
      • Second partition of up to 8 K segments shared among all processes — kept in the global descriptor table (GDT).
    • The CPU generates a logical address; the selector is given to the segmentation unit, which produces a linear address; the linear address is given to the paging unit, which generates the physical address in main memory. Paging units form the equivalent of the MMU. Page sizes can be 4 KB or 4 MB.

    Selector format 9.60 (16 bits):

    sgp
    1312

    s = segment number (13 bits → 213 = 8 K segments per table), g = whether the segment is in the GDT or LDT (1 bit → 2 tables → 16 K segments total), p = protection (2 bits).

    IA-32 paging 9.61, 9.63

    The linear address is translated with two-level paging, 10 / 10 / 12 (p1, p2, d) for 4 KB pages.

    • Page-directory and page-table entries moved to 64 bits in size.
    • Net effect: address space increased to 36 bits — 64 GB of physical memory (236 = 64 G).

    9.20 Example: ARM architecture 9.66

    • Dominant mobile platform chip (Apple iOS and Google Android devices). Modern, energy-efficient, 32-bit CPU.
    • Page sizes: 4 KB and 16 KB pages; 1 MB and 16 MB pages (termed sections).
    • One-level paging for sections, two-level for smaller pages.
    • Two levels of TLBs: the outer level has two micro TLBs (one data, one instruction); the inner is a single main TLB. First the inner is checked, on a miss the outers are checked, and on a miss a page-table walk is performed by the CPU. (This is the slide's wording. The textbook describes translation as beginning at the micro TLBs and falling back to the main TLB; if asked, give the slide's order but know the levels: 2 micro TLBs + 1 main TLB, then a CPU page-table walk.)

    Chapter 9 review

    Summary

    • CPU accesses only registers and main memory; cache bridges the speed gap; protection via base/limit registers (privileged to load), every user-mode address checked.
    • Binding: compile time (absolute code), load time (relocatable code), execution time (needs MMU; logical ≠ physical). Relocation register: physical = relocation + logical; limit check on logical first.
    • Dynamic loading (load routine on first call; no OS support needed) vs dynamic linking (stub, shared libraries, versioning).
    • Contiguous allocation: variable partitions, holes; first-fit / best-fit / worst-fit (first & best better). External vs internal fragmentation; 50-percent rule (1/3 unusable); compaction needs execution-time relocation.
    • Paging: frames (physical) and pages (logical) of equal power-of-2 size; p = high m−n bits, d = low n bits; physical = f × page size + d; no external fragmentation, but internal (avg ½ page, worst 1 page − 1 byte).
    • Page table in memory (PTBR, PTLR) → 2 accesses per reference → TLB (associative, 64–1,024 entries, ASIDs, wired entries). EAT = α·t + (1−α)·2t.
    • Protection bits (r/w/x) and valid–invalid bits; shared pages for reentrant code.
    • Big page tables → hierarchical (10/10/12 on 32-bit; 64-bit needs more levels), hashed (chains; clustered variant), inverted (one entry per frame, pid + page; search via hash).
    • Swapping: backing store, roll out/roll in, time ∝ size (100 MB @ 50 MB/s → 4 s total), pending I/O and double buffering; modern systems swap pages only when memory is very low; mobile systems don't swap.
    • Intel IA-32: segmentation (selector s13/g1/p2, LDT/GDT, 8 K each) then paging (10/10/12, 4 KB or 4 MB pages, CR3); PAE (3-level, 2/9/9/12, 36-bit, 64 GB); x86-64 (48-bit, 4 levels 9/9/9/9/12; 4 KB, 2 MB, 1 GB). ARM: 4/16 KB pages two-level, 1/16 MB sections one-level, micro + main TLBs.

    Logical address space 216 bytes, page size 512 bytes. How many bits for p and d? How many pages?

    Show answer

    n = log2512 = 9 → d = 9 bits, p = 16 − 9 = 7 bits, 27 = 128 pages.

    Page size 1 KB; page table: 0→5, 1→2, 2→7, 3→0. Translate logical addresses 1500 and 3100. What about 4200?

    Show answer

    1500: p = 1, d = 476 → frame 2 → 2×1024 + 476 = 2524. 3100: p = 3, d = 3100 − 3072 = 28 → frame 0 → 28. 4200: p = 4 → not in the table (only 4 pages) → trap (invalid / beyond PTLR).

    Page size 4,096 bytes, process 18,000 bytes. Number of frames and internal fragmentation?

    Show answer

    18,000 / 4,096 = 4 rem 1,616 (4 × 4,096 = 16,384). Frames = 5. Internal fragmentation = 4,096 − 1,616 = 2,480 bytes.

    Memory access 50 ns, TLB hit ratio 90%, ignore TLB time. EAT? Slowdown?

    Show answer

    0.9 × 50 + 0.1 × 100 = 45 + 10 = 55 ns; slowdown 5/50 = 10%.

    Relocation register = 30000, limit = 1200. Logical 1100 → ? Logical 1300 → ?

    Show answer

    1100 < 1200 → physical 31100. 1300 ≥ 1200 → trap (addressing error).

    Holes: 50, 200, 70, 115, 15 KB (in order). Request 60 KB. Which hole is used by first-fit, best-fit, worst-fit?

    Show answer

    First-fit: 200 (first ≥ 60). Best-fit: 70 (smallest ≥ 60, leaves 10). Worst-fit: 200 (largest, leaves 140).

    32-bit address, 4 KB pages, 4-byte entries, single-level table. Size of page table? With two-level 10/10/12, how big is each inner table?

    Show answer

    220 entries × 4 B = 4 MB. Inner table: 210 × 4 B = 4 KB (exactly one page).

    Swap a 200 MB process out and another 200 MB process in, at 100 MB/s. Swap component of context switch?

    Show answer

    200/100 = 2 s each way → 4 s (4000 ms).

    In an inverted page table, what does the index of the matching entry represent? Why is shared memory hard?

    Show answer

    The frame number. Each frame has exactly one entry holding one (pid, virtual page), so two processes can't both map the same frame through the table (only one mapping of a virtual address to the shared physical address).

    Mixed practice quiz (fresh examples)

    Semaphores A = 1, B = 0, shared x = 3. P1: wait(A); x = x + 1; signal(B); signal(A); P2: wait(B); wait(A); x = x * 2; signal(A);. Which final values of x are possible?

    Show answer

    Only 8. B starts at 0, so P2 cannot pass wait(B) until P1 has done x = x + 1 (x = 4) and signal(B). Then P2 needs A, which P1 releases. So x = 4 × 2 = 8 in every interleaving.

    A programmer “optimises” Peterson's algorithm by writing turn = j; before flag[i] = true;. Show that mutual exclusion can fail.

    Show answer

    P0: turn = 1. P1: turn = 0. P1: flag[1] = true; P1 tests flag[0] && turn == 0 → flag[0] is false → P1 enters. P0: flag[0] = true; tests flag[1] && turn == 1 → turn is 0 → P0 enters. Both in the CS — exactly the reordering problem of slide 6.19.

    A lab has 3 printers controlled by a counting semaphore (blocking implementation). Five processes each call wait, and then the first one to get a printer calls signal. What is the semaphore value at the end and how many processes are blocked?

    Show answer

    Init 3 → five waits → 3 − 5 = −2 (two blocked) → one signal → −1, one blocked process woken. Final value −1, one process still blocked.

    Bounded buffer with n = 5. What are the initial values of mutex, full, empty? After the producer has inserted 4 items and the consumer removed 1, what are full and empty?

    Show answer

    Initial: mutex = 1, full = 0, empty = 5. After +4 −1: full = 3, empty = 2.

    Which statement is true? (a) Condition-variable signal increments a counter. (b) A semaphore signal with no waiters is lost. (c) A condition-variable signal with no waiters has no effect. (d) Monitors need explicit wait(mutex) calls by the programmer.

    Show answer

    (c). Semaphore signals are remembered (S++); monitors provide mutual exclusion automatically.

    Banker's. Resources A B C with totals (8, 5, 9). Allocation: T0 (2,0,1), T1 (1,2,0), T2 (2,1,3), T3 (0,1,2). Max: T0 (4,2,3), T1 (3,3,2), T2 (2,2,5), T3 (2,1,4). (a) Available? (b) Need? (c) Safe? (d) T0 requests (2,1,0) — grant? (e) T0 requests (1,1,0) instead — grant? (f) T1 requests (0,2,0) — what happens?

    Show answer

    (a) ΣAllocation = (5,4,6) → Available = (8,5,9) − (5,4,6) = (3,1,3).

    (b) Need: T0 (2,2,2), T1 (2,1,2), T2 (0,1,2), T3 (2,0,2).

    (c) Work (3,1,3): T0 ✗ (B 2 > 1); T1 (2,1,2) ✓ → (4,3,3); T0 ✓ → (6,3,4); T2 ✓ → (8,4,7); T3 ✓ → (8,5,9). Safe: <T1, T0, T2, T3>.

    (d) (2,1,0) ≤ Need (2,2,2) ✓, ≤ Available (3,1,3) ✓. Pretend: Available (1,0,3), Alloc0 (4,1,1), Need0 (0,1,2). Work (1,0,3): T0 (0,1,2) ✗ B; T1 (2,1,2) ✗; T2 (0,1,2) ✗ B; T3 (2,0,2) ✗ A. Unsafe → T0 waits, state restored.

    (e) Pretend: Available (2,0,3), Alloc0 (3,1,1), Need0 (1,1,2). Work (2,0,3): T3 (2,0,2) ✓ → (2,1,5); T0 (1,1,2) ✓ → (5,2,6); T1 ✓ → (6,4,6); T2 ✓ → (8,5,9). Safe → grant.

    A RAG has R1 (2 instances) and R2 (1 instance). T1 holds R2 and requests R1; both R1 instances are held by T2 and T3; T2 requests R2. Is there a cycle? Deadlock?

    Show answer

    Cycle: T1 → R1 → T2 → R2 → T1. But T3 also holds an R1 instance and is not waiting; when T3 releases it, T1 gets R1, finishes, releases R2, then T2 proceeds. Cycle, but no deadlock (multiple instances).

    Which prevention technique is used when every thread must acquire lock_A (#1) before lock_B (#2)? Which condition does it break?

    Show answer

    Total ordering of resources — breaks circular wait.

    16-bit logical addresses, page size 4 KB. Page table: 0→9, 1→3, 2→12, 3→6. Translate 0x2A3C. Then translate 0x5001.

    Show answer

    Show answer

    Offset = log28192 = 13 bits. Inner entries per page = 8192/4 = 2048 = 211 → p2 = 11 bits. Outer p1 = 32 − 13 − 11 = 8 bits. Split: 8 / 11 / 13.

    Memory access = 100 ns, TLB lookup = 20 ns, hit ratio 95%, single-level page table. EAT? (Use the extended formula.)

    Show answer

    Hit: 20 + 100 = 120 ns. Miss: 20 + 100 + 100 = 220 ns. EAT = 0.95 × 120 + 0.05 × 220 = 114 + 11 = 125 ns.

    Page size 8 KB. What is the worst-case and average internal fragmentation per process? A process of 40,960 bytes wastes how much?

    Show answer

    Worst: 8,191 bytes; average: 4,096 bytes. 40,960 / 8,192 = 5 exactly → 0 bytes.

    Relocation register 50000, limit register 8000. For logical addresses 7999, 8000, and 120: physical address or trap?

    Show answer

    7999 → 57999; 8000 → trap (must be < limit); 120 → 50120.

    Holes (in memory order): 300, 600, 350, 200, 750, 125 KB. Requests: 115, 500, 358, 200, 375 KB. Use first-fit.

    Show answer

    115 → 300 (left 185); 500 → 600 (left 100); 358 → 750 (left 392); 200 → 350 (left 150); 375 → 392 (left 17). All satisfied. Final holes: 185, 100, 150, 200, 17, 125.

    IA-32 with 4 MB pages: why is the offset 22 bits, and which table level is skipped?

    Show answer

    4 MB = 222 bytes, so 22 offset bits. The page directory entry points straight to the 4 MB page, skipping the page table level (bits 31–22 = directory, 21–0 = offset).

    Swapping: a 512 MB process is swapped out and a 256 MB process swapped in at 128 MB/s. Total swap time?

    Show answer

    512/128 = 4 s out + 256/128 = 2 s in = 6 s (6000 ms).

    Match the page-table type: (a) one entry per physical frame; (b) virtual page number goes through a hash, chains compared; (c) page number split into p1 and p2.

    Show answer

    (a) inverted; (b) hashed; (c) hierarchical (forward-mapped).

    Readers–writers (first variant): a writer W is waiting, R1 is reading, and R2 arrives. Does R2 read before W writes? What changes in the second variant?

    Show answer

    First variant: yes — read_count > 0, so R2 doesn't touch rw_mutex and reads immediately (W may starve). Second variant: once W is ready, newly arrived R2 must wait.

    Name the liveness problem and the fix: a high-priority thread waits on a lock held by a low-priority thread, which is preempted by medium-priority threads.

    Show answer

    Priority inversion; priority-inheritance protocol.
