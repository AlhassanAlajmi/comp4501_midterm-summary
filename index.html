1.1 What is a Database?
DATABASE (DB) 🔴 CRITICAL

Definition: A collection of related data — data that can be recorded and that have implicit meaning.

Summary form: A collection of related data (recorded facts) that reflects some aspect of the real world and is used for specific purposes.

Examples: Amazon.com, Muscat Bank, SQU Library.

Essential properties of a database (3)

  1. Represents some aspect of the real world — called the mini-world or Universe of Discourse (UoD); it interacts with events in the real world.
  2. Logically coherent collection of data with inherent meaning — it cannot be random data; there must be a source the data are derived from.
  3. Designed and built for a specific purpose — there is an audience (users) actively interested in its contents.

Database types (5)

TypeWhat it stores / doesLecture example
Traditional database applicationsTextual or numeric information (everyday storage & retrieval)Dormitory DB storing residents, rooms, rentals
Multimedia databasesImages, audio clips, video streams (digitally)University DB storing recorded lectures, project videos, images
Geographic Information Systems (GIS)Store and analyze maps, weather data, satellite imagesCampus GIS showing buildings, roads, facilities

🧠 What to Remember
  • DB = collection of related data with implicit meaning — not random data.
  • 3 properties: mini-world / UoD, logically coherent, specific purpose & users.
  • OLAP / data warehouse → decision making; real-time/active → control processes.

1.2 Database Management System (DBMS)
DBMS 🔴 CRITICAL

Definition: A collection of programs (software system) that enables users to define, create (construct), maintain, manipulate and share a database.

Summary form: A generalized software package for implementing and maintaining a computerized database (lecture: “Database + Software = DBMS”).

DBMS functions

FunctionMeaning
DefiningIdentify the data types, structures, and restrictions (constraints) of the data to be stored
ConstructingThe process of storing the data so that it can be controlled by the DBMS
ManipulatingQuery, update the database, and generate reports
MaintainingAllow the system to develop/evolve as requirements change over time
SharingAllow multiple users and programs to access the database at the same time
ProtectingSystem protection (against hardware/software crashes) + Security protection (against unauthorized access)

DBMS concepts

META-DATA 🔴 CRITICAL

Definition: The database definition or descriptive information about the data, stored by the DBMS in a database catalog or dictionary.

In simple words: “data about the data”. The DB stores the actual data (students, rooms, rentals); the catalog stores its description.

Catalog stores: table definitions, attribute names & data types, keys & constraints (e.g. NOT NULL, CHECK), relationships between tables, indexes, users & privileges, view definitions, stored procedure definitions.

Example: Dormitory table ROOM — meta-data: RoomNo VARCHAR(5) (primary key), RoomType VARCHAR(10), MonthlyRent DECIMAL(6,2), Status VARCHAR(10) (Available / Occupied). The actual rows (R12, 80, Available) are the data.

Application program
Accesses the database by sending queries or transactions to the DBMS.
Query
A request for specific data; causes some data to be retrieved.
e.g. SELECT * FROM Room WHERE Status = 'Available';
Transaction
May cause some data to be read and some data to be written into the database.
e.g. “Rent a room”: INSERT INTO Rental … then UPDATE Room SET Status='Occupied' WHERE RoomNo='R12';
Query vs Transaction
Query → retrieves data only.   Transaction → may read and write (insert/update) data.
The difference: a transaction changes the database; a query just reads it.

1.4 File Processing vs Database Approach
Traditional file processingDatabase approach
Each user defines and implements the files needed for a specific applicationSingle repository — data defined once, then accessed by various users
Updates cause inconsistency; hard to keep up to date (scalability); other users may not be aware of latest changesData shared & kept consistent by the DBMS
Data redundancy → duplication of effort + wasted storageRedundancy controlled
Files = each application owns its own data (redundant, inconsistent). Database = one shared repository, defined once.

4 characteristics of the database approach 🔴 CRITICAL

  1. Self-describing nature of a database system
  2. Insulation between programs and data, and data abstraction
  3. Support of multiple views of the data
  4. Sharing of data and multiuser transaction processing

1 · Self-describing nature

The database system contains a complete definition of its structure and constraints (meta-data) — structure of each file/record, types and storage format of each data item. It is stored in the catalog, which is used by:

  • the DBMS software, and
  • database users who need information about the database structure.

Because of this, DBMS software can work equally well with any number of database applications as long as their definitions are provided — it extracts the definition from the catalog.

2 · Insulation between programs and data

Program–data independence 🔴

The structure of data files is stored in the DBMS catalog separately from the access programs, so the file structure can be changed without affecting the programs.

Example: add attribute BirthDate to STUDENT → the student application does not change; the DBMS uses the catalog.

Program–operation independence 🔴

Operations are specified in two parts: interface (operation name + data types of its arguments) and implementation. The implementation can change without affecting the interface.

Example: CalculateRent(RoomNo) changes from MonthlyRate to MonthlyRate + ServiceFee; the dormitory application still calls it the same way.

Program–data independence = change the data structure. Program–operation independence = change an operation's implementation (interface stays the same).
DATA ABSTRACTION 🔴

Definition: Allows program-data independence and program-operation independence. The DBMS gives users a conceptual representation of data that does not include details of how data is stored or how operations are implemented.

In simple words: users see what the data means (STUDENT —Enrolls— COURSE), not how it is stored (record length, starting byte, access paths).

Lecture example (conceptual representation): Professor —Advises— Student; Professor —Teaches— Course; Student —Takes— Course; Student —TAs— Course; attributes such as Salary, Tenure, GPA, Rating.

DATA MODEL

Definition: A type of data abstraction: a set of concepts used to describe the structure of data, relationships, and constraints — how data is structured, related and constrained in a database.

3 · Support of multiple views

  • A view can be a subset of the database, or contain virtual data derived from the database files but not explicitly stored (e.g. output of a query, a calculated GPA).
  • A multiuser DBMS whose users have a variety of distinct applications must provide facilities for defining multiple views (e.g. a different view for students' advisors than for the finance department).

4 · Sharing of data and multiuser transaction processing

  • Allows multiple users to access the database at the same time.
  • Concurrency control software: ensures several users trying to update the same data do so in a controlled manner so the result is correct.
  • OLTP (Online Transaction Processing) applications — e.g. travel agents, hotel reservations — ensure simultaneous transactions operate efficiently.
TRANSACTION 🔴

Definition: An executing program or process that includes one or more database accesses (reading or updating records).

Isolation property: each transaction appears to execute in isolation from other transactions (others cannot see its intermediate changes).

Atomicity property: either all the database operations of a transaction are executed or none are (“all or nothing”).

Example: bank transfer from account1 to account2. Registering S101 for CSE2101: (1) check available seats → (2) insert ENROLLMENT record → (3) update registered count → (4) update student credits. If step 3 fails, the enrollment record is also not inserted — the DB is rolled back (atomicity). Two students registering at the same time: T2 does not see T1's intermediate updates (isolation).

Isolation vs Atomicity
Isolation → transactions don't see each other's intermediate changes.
Atomicity → a transaction runs completely or not at all.
The difference: isolation is about concurrent transactions; atomicity is about one transaction finishing fully.
🧠 What to Remember
  • 4 characteristics: self-describing, insulation/abstraction, multiple views, sharing & multiuser transactions.
  • Catalog is used by the DBMS software and by users.
  • A view may hold virtual (derived) data not stored.
  • Concurrency control = correct results when many users update the same data.

1.5 Advantages of Using the DBMS Approach

The lecture numbers 10 advantages. Learn the list, then the key detail of each.

#AdvantageKey details from lecture
1Controlling redundancyData normalization: store each logical item (e.g. student name, birth date) in one place → consistency + saves storage. Denormalization: some values repeated in several files (e.g. student name and course number in GRADE_REPORT) — controlled redundancy sometimes needed to improve query performance; the DBMS automatically enforces consistency checks.
2Restricting unauthorized accessType of access (retrieval/update) controlled by a security and authorization subsystem; the DBA uses privileged software to create accounts and specify restrictions; the DBMS enforces them automatically.
3Persistent storage for program objectsFor object-oriented DB systems: complex objects (e.g. C++ class objects) stored permanently. Avoids the impedance mismatch problem (traditional DB data structures incompatible with programming-language data structures). Persistent = data remains stored after the program terminates.
4Storage structures & search techniques for efficient query processingIndexes (tree/hash structures) speed up disk search; buffering & caching module keeps parts of DB in main memory; query processing & optimization module selects an efficient execution plan.
5Backup and recoveryRecovery from hardware/software failures: transaction resumed from the interruption point or DB restored to the state before the interruption; disk backup essential for disastrous disk failure.
6Multiple user interfacesUsers with different technical knowledge → variety of interfaces (GUIs).
7Representing complex relationshipsRepresent varied relationships, define new ones when needed, easily retrieve/update related data (e.g. instructor offers several courses each semester).
8Enforcing integrity constraintsData type (Grade ∈ {A,B,C,D,F,I}); referential integrity (every section record must relate to a course record); key/uniqueness (unique student_number); business rules (checked by update programs or at data entry); inherent rules of the data model (grade ‘Z’ invalid).
9Permitting inferencing and actions using rulesDeductive DB: deduction (inference) rules derive new info from stored facts (e.g. which students are on probation; “if a student takes a course and passes it → completed”). Stored procedures: more involved procedures invoked when conditions are met. Active DB: automatically responds to active rules (e.g. stock < 10 units → automatic restock order, no user intervention).
10Additional implicationsFlexibility: change DB structure gradually without affecting stored data (e.g. add RoomType column). Availability of up-to-date information: updates visible immediately to all authorized users (e.g. travel agency, student registration).

A database system that automatically reacts to conditions based on predefined rulesA specific database object that executes automatically when a specified event occurs (INSERT, UPDATE, DELETE)

🧠 What to Remember
  • Normalization = one place; denormalization = controlled redundancy for performance.
  • Impedance mismatch → solved by object-oriented DBs; persistent = survives program end.
  • Indexes, buffering/caching, query optimization → efficient query processing.
  • Deductive (inference rules) · stored procedures · active DB (automatic reaction).

2.1 Data Models and Their Categories

Basic client/server DBMS architecture: the client module handles user interaction and provides the user interface; the server module handles data storage, access and search.

DATA ABSTRACTION

Hiding details of data organization and storage, and highlighting the essential features for an improved understanding of data. Different users can see data at their preferred level of detail.

DATA MODEL 🔴 CRITICAL

Definition: A collection of concepts that describe the structure of a database — data types, relationships and constraints that apply to the data. It provides the means to achieve data abstraction.

Also includes: basic operations to specify retrievals and updates, and the dynamic aspect (behavior) of an application — the designer can specify valid user-defined operations, e.g. COMPUTE_GPA applied to a STUDENT object.

Categories of data models (based on concepts used to describe DB structure) 🔴

Concepts: entity (real-world object or concept, e.g. a student), attribute (property that describes an entity, e.g. student name), relationship (association among two or more entities, e.g. employee–project). Example: Entity-Relationship (ER) model.End users

Examples in lecture: relational data model (used most frequently in traditional commercial DBMSs); object data model (newer family of higher-level implementation models, closer to conceptual models; used in software engineering).Both

  • 3 categories: conceptual (users, ER), representational (relational), physical (storage, access paths, indexes).
  • Data model = structure + relationships + constraints (+ operations/behavior).

2.2 Schemas, Instances, and Database State

In any data model it is essential to distinguish between the description of the database (catalog) and the database itself.

DATABASE SCHEMA 🔴 CRITICAL

Definition: The description of a database. Specified during the design phase and not changed frequently.

Aspects described: data types of data items, relationships, constraints (e.g. prerequisite for majoring in CS).

  • Schema diagram: displays selected (some) aspects of the schema; shows the structure of records but not the instances of records (Figure 2.1: STUDENT, COURSE, PREREQUISITE, SECTION, GRADE_REPORT with their attribute names).
  • Schema construct: each object in the schema (e.g. STUDENT, COURSE).
  • Database instance: refers to the individual records (actual students' info).
DATABASE STATE (SNAPSHOT) 🔴

The data in the database at a particular moment in time.

StateMeaning
Empty stateWhen a new database is defined: schema specified to the DBMS, no data yet
Initial stateDatabase first populated / loaded with initial data
Valid stateSatisfies the structure and constraints specified in the schema (e.g. StudentID unique, Name not null)
  • Specifying a correct schema is of utmost importance. The DBMS stores the description of schema constructs and constraints (meta-data).
  • Schema evolution: changes applied to the schema as application requirements change (this changes the database's current state).
SchemaInstance / State
Description of the DB — structure, types, constraintsActual data at a moment in time
Defined at design time; changes rarely (schema evolution)Changes every time data is inserted/deleted/updated
Shown in a schema diagram (no records)Shown as tables filled with rows
Schema = the description (rarely changes). State = the data now (changes often).
🧠 What to Remember
  • Schema diagram shows some aspects and no instances.
  • States: empty → initial → (must always be) valid.

2.3 Three-Schema Architecture and Data Independence

Proposed to achieve the main DBMS characteristics: self-describing nature (by storing the schema), data/program/operation independence, and support of multiple user views.

Goal: separate physical storage from user applications.

LevelDescribes
Internal levelThe physical storage structure of the database
Conceptual levelStructure of the whole database for a community of users — entities, data types, relationships, user operations and constraints
External (view) levelThe part of the database a particular user group is interested in, hiding the rest
MAPPING

The process of transforming requests and results between levels. How to map between levels is stored in the catalog; the DBMS uses software + catalog to ensure correct mapping.

Data independence 🔴 CRITICAL

DATA INDEPENDENCE

Definition: The capacity to change the schema at one level without having to change the schema at the next higher level (only the mapping between the levels changes).

Logical data independencePhysical data independence
Change atConceptual schemaInternal schema
Without changingExternal schemas / application programsConceptual schema
What changesWHAT data is stored / how it is structuredHOW data is stored or accessed
Lecture exampleAdd/remove a record type or data item — e.g. add attribute Floor to ROOM; an application using only RoomNo and Rent still worksCreate an additional access structure — e.g. add an index on RoomNo; table and application stay the same, searching becomes faster
Logical = conceptual changes hidden from external views. Physical = internal (storage) changes hidden from the conceptual schema.
🧠 What to Remember
  • Goal: separate physical storage from user applications.
  • Levels bottom→top: internal → conceptual → external.
  • Data independence: change one level, the next higher level is unaffected; only the mapping changes.
  • Adding an index = physical; adding an attribute = logical.

2.6 Centralized and Client/Server Architectures
CENTRALIZED DBMS ARCHITECTURE

(Past) All DBMS functionality, application program execution and user-interface processing carried out on one machine; users connect via terminals (Figure 2.4). Gradually DBMSs used processing power at the user side → client/server DBMS developed.

Basic client/server architecture

  • Specialized servers: file server (maintains client machines' files), printer server (all print requests forwarded to it), web / e-mail servers. Their resources are accessible by many clients.
  • Client: user machine providing user-interface capabilities and local processing.
  • Server: system containing both hardware and software that provides services to clients (file access, printing, archiving, database access).

Two-tier client/server 🟡

Server handles
Query and transaction functionality related to SQL processing, data storage, local concurrency control, buffering.
Client handles
User interface programs and application programs, data dictionary functions.

The DBMS interacts with programming-language compilers, global query optimization, concurrency control and recovery across multiple servers. The exact distribution of functions varies between systems.

Three-tier and n-tier (Web applications) 🟡

An application server or web server adds an intermediate layer between client and database server. It runs application programs and stores business rules, and provides security by checking the client's qualifications before applying a request.

ClientPresentation layer — display info, allow data entry
⇄
Application / Web serverBusiness logic layer — intermediate rules/constraints; formats query results into dynamic web pages
⇄
Database serverDatabase services layer — data management services

Flow: accept client request → process it and send DB queries to the DB server → process/filter the data further to present to the user in GUI format.

N-tier: divides the layers between the user and the stored data into finer components — e.g. Tier 0 client with web browser → Tier 1 web server → Tier 2 application server → Tier 3 database server / DBMS.

🧠 What to Remember
  • Centralized = everything on one machine.
  • 2-tier: server = SQL/query/transactions/storage; client = UI + application programs.
  • 3-tier: middle tier (application/web server) runs apps, stores business rules, checks security.

Domains, attributes, tuples, relations 🔴 CRITICAL

DOMAIN D

Definition: A set of atomic values. Atomic = each value is indivisible (single).

Specifying a domain: give it a name, data type and format.

Same domain, different roles: Usa_phone_number can play the role of mobile_phone, office_phone and/or home_phone.

Lecture examples: Usa_phone_numbers — ten-digit numbers, format (ddd)ddd-dddd; Grade_point_averages — real number between 0 and 4; Employee_ages — integer between 15 and 80; Academic_department_codes — ‘CS’, ‘ECON’, ‘PHYS’.

RELATION SCHEMA R

Denoted R(A1, A2, …, An) — a relation name R and a list of attributes.

Attribute Ai = the name of a role played by some domain D in schema R.

Degree (arity) = number of attributes n. E.g. Student(Name, Phone, Major, Age) has degree 4.

RELATION (RELATION STATE) r(R)

A set of n-tuples r = {t1, t2, …, tm}. Each n-tuple t is an ordered list of n values t = <v1, …, vn>, where each vi is an element of dom(Ai) or the special NULL value.

Mathematically: a relation of degree n on the domains, i.e. a subset of the Cartesian product of the domains:
r(R) ⊆ dom(A1) × dom(A2) × … × dom(An)

Cardinality |D| = total number of values in a domain (assume finite). Total possible combinations = |dom(A1)| × |dom(A2)| × … × |dom(An)|.

What this means: the Cartesian product gives all possible combinations; the relation contains only the combinations that represent actual data.

Current relation state = the relation state at a given time; reflects only valid tuples representing a particular state of the real world.

Notation

  • R.A — attribute qualified with its relation (dot notation), e.g. Student.Name.
  • t = <v1, …, vn> — vi is the value for attribute Ai.
  • t[Ai] and t.Ai both = value vi of t for Ai.
  • t[Au, Aw, …, Az] = sub-tuple of values for those attributes.

3.2 Characteristics of Relations
RULE — Ordering of tuples

Rule: A relation is a set of tuples; elements have no order. A relation is not sensitive to tuple order.

Example: Figure 3.2 shows STUDENT with the same 5 tuples in a different order — it is the same relation.

RULE — Ordering of values within a tuple

Tuple ordering is not part of a relation definition. The order of attributes and values is not that important as long as the correspondence between attributes and values is maintained.

Alternative definition: a tuple is a set of (<attribute>, <value>) pairs; each pair maps attribute Ai to a value vi from dom(Ai) (Figure 3.3: two identical tuples written with attributes in different orders).

Lecture choice: use the first definition — attributes and values within tuples are ordered — because it is a simpler notation.

RULE — Values are atomic (flat relational model)

Each value in a tuple is atomic. Composite and multivalued attributes are not allowed.

• Multivalued attribute (e.g. locations of a department) → must be represented by a separate relation.
• Composite attribute (e.g. Name(first, mid, last)) → represented only by its simple component attributes.

3.4 Domain, Key and NULL Constraints
DOMAIN CONSTRAINT

Within each tuple, the value of each attribute A must be an atomic value from dom(A). Typical data types: numeric (integers, reals), characters, Booleans, fixed-length strings, variable-length strings, date/time/timestamp, money, other special types.

RULE — Key constraint

Rule: No two tuples can have the same combination of values for all their attributes (no duplicate tuples) — and no two tuples can share the same value for a key.

SUPERKEY (SK)

One or more attributes that uniquely identify each tuple. May contain unnecessary (extra) attributes.

Example: {Student_ID, Name}

KEY (K) = MINIMAL SUPERKEY 🔴

A superkey that is minimal: removing any attribute makes it lose uniqueness. A key may be a single attribute or multiple attributes.

Example: {Student_ID}

Key properties (2): (1) Uniqueness — no two tuples have the same values for all key attributes; (2) Minimal superkey — you cannot remove any part and keep uniqueness. If a key is (First_Name, Last_Name) and removing one breaks uniqueness, the full combination is the minimal key.

Every key is a superkey, but not every superkey is a key.
Lecture practice — superkey or key?

• {Car Plate #, Engine Licence #}: the lecture lists car plate number and engine serial number as two separate candidate keys → each alone is unique → the pair is a superkey, not a key (not minimal).

• {Bank_code, Branch#, EmployeeID}: apply the test — it is a key only if you cannot drop any attribute (e.g. EmployeeID is unique only within a branch of a bank). If EmployeeID alone is unique, the set is just a superkey. State your assumption.

CANDIDATE KEY

A relation schema may have more than one key; each is a candidate key. E.g. student number & student mobile number; car plate number & engine serial number.

PRIMARY KEY (PK) 🔴

Designated among the candidate keys; its value is used to identify tuples. Underlined in the schema. Other candidate keys are designated as unique keys and are not underlined.

Figure 3.4 — CAR
CAR(License_number, Engine_serial_number, Make, Model, Year) — License_number = PK; Engine_serial_number = other candidate key (unique, not underlined).
NOT NULL CONSTRAINT

Specifies whether NULL values are or are not allowed for an attribute. E.g. if every student must have a Name, Name is constrained NOT NULL — users cannot leave it empty.

🧠 What to Remember
  • Superkey ⊇ key; key = minimal superkey.
  • Candidate keys → one chosen as PK (underlined); others = unique keys.

3.5 Entity Integrity, Referential Integrity & Foreign Keys
RULE — Entity integrity constraint 🔴

Rule: No primary key value can be NULL.

Why: the PK is used to identify tuples; a NULL could not identify anything.

Exam reminder: inserting a tuple with NULL PK → rejected (entity integrity violation).

RULE — Referential integrity constraint 🔴

Rule: Specified between two relations; maintains consistency among their tuples. A foreign key value must match a primary key value of some tuple in the referenced relation (or be NULL).

Example: EMPLOYEE.Dno — its value in every employee tuple must match the Dnumber of some tuple in DEPARTMENT.

3.6 Update Operations and Constraint Violations

Relational operations = retrievals and updates. Basic operations that change the state: Insert, Delete, Update (Modify).

RULE — INSERT can violate ALL FOUR constraint types

Insert provides a list of attribute values for a new tuple t into R. It can violate:

  • Domain: value of wrong data type (e.g. insert grade ‘T’)
  • Key: key value already exists in another tuple
  • Entity integrity: primary key is NULL
  • Referential integrity: FK value refers to a tuple that does not exist (e.g. insert Dno 6 for an employee when no department 6)

If violated: default = reject the insertion; other options depend on the violation (e.g. DBMS asks the user to first insert a valid PK).

RULE — DELETE can violate ONLY referential integrity

Happens when the deleted tuple is referenced by foreign keys of other tuples (e.g. delete a department). Options:

  • Restrict — reject the deletion
  • Cascade — propagate: automatically delete the tuples that reference the deleted tuple
  • Set null / set default — change the referencing FK values to NULL (or default). Cannot set NULL if the FK is part of a primary key.

The DBMS lets designers specify which option applies.

RULE — UPDATE

Needs a condition to select the tuple(s) to modify.

  • Attribute not part of PK or FK → usually no problem (only domain check).
  • Updating a PK/FK → similar issues as insert/delete. E.g. update an employee's Dno to 7 (no dept 7) → referential violation; update Ssn to ‘123’ which already exists → key violation.

Among n entity types E1, …, En: defines a set of associations among entities from these types.

7.4 Constraints on Binary Relationships
CARDINALITY RATIO 🔴 CRITICAL

Definition: Specifies the maximum number of relationship instances that an entity can participate in.

Types:

  • 1:1 — e.g. EMPLOYEE MANAGES DEPARTMENT
  • 1:N (or N:1) — e.g. a department has several employees; the N is placed on the employee side
  • M:N — a project can have N employees and an employee can work on M projects
PARTICIPATION CONSTRAINT 🔴 CRITICAL

Definition: Specifies whether the existence of an entity depends on its being related to another entity (the minimum).

  • Total (= existence dependency) — double line. E.g. every employee must work for a department.
  • Partial — single line. E.g. some employees manage a department.
STRUCTURAL CONSTRAINTS

The combination of cardinality ratio and participation constraints (see Figure 7.2) — can be written with (min, max) notation.

Cardinality ratio vs Participation
Cardinality ratio → the maximum (1 or N).
Participation → the minimum / existence dependency (total or partial).
The difference: “at most how many?” vs “must it participate at all?”

Attributes of relationship types 🟡

RULE — Where can a relationship attribute go?
  • 1:1: may be migrated to either participating entity type (e.g. Manager_start_date of MANAGES → EMPLOYEE or DEPARTMENT).
  • 1:N: may be migrated only to the entity on the N-side (e.g. Start_date of WORKS_FOR → EMPLOYEE, not DEPARTMENT).
  • M:N: some attributes are determined by the combination of participating entities → must stay as relationship attributes (e.g. Hours of EMPLOYEE WORKS_ON PROJECT).

7.5 (min, max) Notation — Alternative ER Notation
RULE — (min, max) structural constraint 🔴

Rule: Associate a pair of integers (min, max) with each participation of an entity type E in a relationship type R, where 0 ≤ min ≤ max and max ≥ 1. For each entity e in E, e must participate in at least min and at most max relationship instances in R at any point in time.

Why: it replaces the cardinality ratio (1:1, 1:N, M:N) and the single/double-line participation notation.

Exam reminder: participation is total if min > 0, otherwise (min = 0) partial.

Where the numbers go: ratio vs (min,max)
1:N ratio → N is written on the many side (EMPLOYEE side of WORKS_FOR).
(min,max) → beside each entity: how many instances each of its entities joins — EMPLOYEE (1,1), DEPARTMENT (4,N).
The difference: the “N” appears beside EMPLOYEE in ratio notation but beside DEPARTMENT (as max) in (min,max) notation.

Lecture practice: Q7.36 (BANK schema: BANK –BRANCHES (1:N)– BANK_BRANCH (weak, partial key Branch_no); ACCTS and LOANS (1:N) to ACCOUNT and LOAN; A_C and L_C (M:N) to CUSTOMER) · Exercise on Figure 7.22 (EMPLOYEE WORKS_IN DEPARTMENT, HAS_PHONE, CONTAINS with PHONE) · Exercise on Figure 7.32 (INSTRUCTOR TEACHES COURSE USES TEXT; course uses ≤ 5 books; instructors teach 2–4 courses) · Airline schema Figure 7.20.

🧠 What to Remember
  • 0 ≤ min ≤ max, max ≥ 1.
  • min = 0 → partial; min ≥ 1 → total.
  • (min,max) replaces both ratio and single/double lines.

7.6 Relationships of Degree Higher than Two (Ternary)
TERNARY RELATIONSHIP 🔴

A relationship type of degree three. E.g. SUPPLY instance (s, j, p): supplier s supplies part p to project j.

RULE — Reading cardinality in a ternary relationship

Rule: The number beside an entity = the maximum number of relationship instances for that entity when the other two entities are fixed. “Fix the other two, then ask how many of this entity?”

Example (N : N : 1): N near SUPPLIER → for a fixed (Part, Project) there can be many suppliers · N near PART → for a fixed (Supplier, Project) many parts · 1 near PROJECT → for a fixed (Supplier, Part) at most one project.

Participation: total (double line) — every project must receive at least one part from a supplier. Partial (single line) — a supplier may exist without supplying anything; a part may exist without being supplied.

1 : M : N example
(ABC, Laptop, Project A), (ABC, Laptop, Project B), (ABC, Monitor, Project A): Project A + Laptop → supplied by ABC only; ABC + Laptop → many projects; ABC + Project A → many parts. Constraints on ternary (n-ary) relationships

  • Two notations — cardinality ratio (1, M or N) and (min, max) — should both be used if it is important to fully specify structural constraints.
  • If all n cardinalities are M or N, the identifying key of the relationship = the combination of all n participants.
  • Example: with 1 beside SUPPLIER, instance (s, j, p) is uniquely identified by its (j, p) combination → (j, p) is the key (Figure 7.16c).

Ternary vs three binary relationships 🔴

RULE — Three binaries ≠ one ternary

Rule: The existence of three binary relationship instances (s,p), (j,p), (s,j) does not imply an instance (s,j,p).

Example (Figure 7.17): SUPPLY(SUPPLIER, PROJECT, PART) vs SUPPLIES (SUPPLIER–PROJECT, M:N), CAN_SUPPLY (SUPPLIER–PART, M:N), USES (PROJECT–PART, M:N). The binaries are not equivalent to SUPPLY.

Example (Figure 7.18): OFFERS(INSTRUCTOR, SEMESTER, COURSE) vs binaries CAN_TEACH, TAUGHT_DURING, OFFERED_DURING. Facts: Ahmed taught Database in Spring 2026; Ahmed taught Programming in Fall 2026; Database was taught by Sara in Fall 2026. The binaries still say Ahmed–Database, Ahmed–Fall 2026, Database–Fall 2026 — but we cannot conclude “Ahmed taught Database in Fall 2026” ✗.

If CAN_TEACH were 1:1: one instructor can teach only one course, and one course can be taught by only one instructor.

Choosing between binary and ternary

  • Some design tools permit only binary relationships → a ternary must be represented as a weak entity type with no partial key and three identifying relationships (Figure 7.16c: weak SUPPLY with identifying SS to SUPPLIER, SPJ to PROJECT, SP to PART — each 1:N, SUPPLY on the N side).
  • Or represent it as a regular entity type by introducing an artificial (surrogate) key (e.g. Supply_ID).
Lecture exercise — Physician / Patient / Treatment
Requirements: a physician with a specific patient can follow M treatments; a physician follows a specific treatment for N patients; a patient is followed in a specific treatment by one physician. Ternary FOLLOW is converted into a weak entity FOLLOW with three binary identifying relationships: PHYSICIAN –PHF (1:N)– FOLLOW, PATIENT –FP (1:N)– FOLLOW, TREATMENT –FT (1:N)– FOLLOW.
Figure 7.19 — weak entity with a ternary identifying relationship
Requirement: a candidate can have multiple interviews with the same company but with different departments on separate dates; the job offer is based on only one interview. → INTERVIEW is a weak entity identified through ternary identifying relationship CCI with CANDIDATE and COMPANY (attributes Department, Date / Dept_date); INTERVIEW —RESULTS_IN— JOB_OFFER.

Design choices for ER conceptual design

  • Model a concept first as an attribute, then refine it into a relationship if it is a reference to another entity type.
  • An attribute that exists in several entity types may be elevated to an independent entity type.
  • The inverse also works: identify entities first, then their attributes, then refine.
  • Specify relationships between entities along with their degree.
🧠 What to Remember
  • Ternary number = max when the other two are fixed.
  • (s,p),(j,p),(s,j) ⇏ (s,j,p).
  • Binary-only tools: ternary → weak entity (no partial key, 3 identifying rels) or regular entity with surrogate key.
  • All M/N → key is the combination of all participants.

The Enhanced Entity-Relationship (EER) Model

Subclasses & superclasses · inheritance · specialization & generalization · constraints · hierarchies & lattices · categories (union types) · design choices · abstraction concepts

7.7 EER Basics: Subclasses, Superclasses, Inheritance
EER MODEL 🔴

Created to design more accurate database schemas — reflecting data properties and constraints more precisely — for applications with more complex requirements than traditional ones.

EER includes all ER concepts, plus: subclasses and superclasses · specialization and generalization · category or union type · attribute and relationship inheritance.

SUBCLASS (SUBTYPE) 🔴

A meaningful subgrouping of the entities of an entity type, represented explicitly because of its significance to the application. E.g. EMPLOYEE → SECRETARY, ENGINEER, TECHNICIAN, MANAGER, …

Names for the superclass–subclass link: superclass/subclass, supertype/subtype, class/subclass relationship.

TYPE INHERITANCE 🔴

A subclass entity inherits all attributes and relationships of its superclass.

In simple words: every SECRETARY is an EMPLOYEE, so a secretary also has Name, Ssn, Birth_date, Address — plus its own Typing_speed.

Superclass vs Subclass
Superclass → the general entity type (EMPLOYEE); holds the common attributes.
Subclass → a subset of the superclass's entities (SECRETARY); inherits everything and may add specific attributes and specific relationships.
The difference: every subclass member is also a superclass member, not the other way round.
🧠 What to Remember
  • EER = ER + subclass/superclass + specialization/generalization + category (union) + inheritance.
  • Subclass inherits all attributes and relationships.

7.8 Specialization and Generalization
SPECIALIZATION 🔴

Definition: The process of defining a set of subclasses of an entity type, on the basis of some distinguishing characteristic of the entities in the superclass.

Approach: Top-down conceptual refinement — start with an entity type, then define subclasses by successive specialization.

GENERALIZATION 🔴

Definition: The process of defining a generalized entity type from the given entity types — the reverse process of abstraction; generalize into a single superclass, and the original entity types become special subclasses.

Approach: Bottom-up conceptual synthesis. Example: {CAR, TRUCK} → VEHICLE.

Specialization = top-down (superclass → define subclasses). Generalization = bottom-up (existing entity types → common superclass).

What a specialization allows

  • Define a set of subclasses for an entity type.
  • Establish additional specific attributes for each subclass — attributes that apply to some but not all superclass entities (e.g. Typing_speed for SECRETARY).
  • Establish additional specific relationship types between a subclass and other entity types or subclasses — relationships only subclass members participate in (e.g. HOURLY_EMPLOYEE BELONGS_TO TRADE_UNION).
Why specialize? (lecture table)
If all employees sit in one table, specific attributes become NULL for most rows: E101 Ahmed Technician (Typing_speed NULL, Tgrade T2, Eng_type NULL); E102 Sara Secretary (Typing_speed 65, others NULL); E103 Ali Engineer (Eng_type Civil, others NULL)… Subclasses hold these specific attributes instead. Figure 7.20 shows instances: an employee entity (e.g. e1) also appears in exactly one of SECRETARY / ENGINEER / TECHNICIAN.
Generalization examples
Figure 8.3: CAR(Vehicle_id, Price, License_plate_no, Max_speed, No_of_passengers) and TRUCK(Vehicle_id, Price, License_plate_no, No_of_axles, Tonnage) → common attributes move to superclass VEHICLE(Vehicle_id, Price, License_plate_no); CAR keeps Max_speed, No_of_passengers; TRUCK keeps No_of_axles, Tonnage (disjoint).
Another: STUDENT(ID, Name, Email, Major, GPA) and INSTRUCTOR(ID, Name, Email, Salary) → PERSON(PersonID, Name, Email) with subclasses STUDENT(Major, GPA), INSTRUCTOR(Salary).
🧠 What to Remember
  • Specialization: top-down, by a distinguishing characteristic. Generalization: bottom-up, {Car, Truck} → Vehicle.
  • Subclasses add specific attributes and specific relationships.

7.9 Constraints on Specialization / Generalization
  • Constraints apply to a single specialization or a single generalization.
  • We may have several specializations on the same entity type (e.g. by job type, by method of pay).
  • A specialization may consist of a single subclass only, such as {MANAGER}.

Disjointness constraint 🔴 CRITICAL

DISJOINT — “d”

Subclasses must be disjoint: an entity can be a member of at most one subclass of the specialization.

OVERLAPPING — “o”

The same real-world entity may be a member of more than one subclass of the specialization.

Figure 8.5: PART → o → MANUFACTURED_PART, PURCHASED_PART.

Completeness (totalness) constraint 🔴 CRITICAL

TOTAL — double line

Every superclass entity must belong to at least one subclass. E.g. every EMPLOYEE must be either HOURLY or SALARIED.

PARTIAL — single line

Some superclass entities may belong to no subclass. E.g. not all employees are managers.

The single/double line notation is similar to partial/total participation of an entity type in a relationship (Chapter 7, Part A).

RULE — Disjointness and completeness are independent

Four possible combinations (lecture examples):

RULE — Insertion and deletion rules 🔴
  • Delete an entity from a superclass → it is automatically deleted from all subclasses it belongs to.
  • Insert an entity into a superclass → it MUST be inserted into all predicate-defined (or attribute-defined) subclasses whose defining predicate it satisfies (overlapping).
  • Insert into a superclass with total specialization → it MUST be inserted into at least one subclass.
Disjoint/overlapping vs Total/partial
Disjoint vs overlapping → can an entity be in more than one subclass? (letter d / o in the circle)
Total vs partial → must every entity be in at least one subclass? (double / single line from superclass to circle)
The difference: one is about the maximum number of subclasses, the other about the minimum.
🧠 What to Remember
  • d = at most one subclass; o = may be in several.
  • Double line = total (at least one); single = partial.
  • 4 independent combos. Attribute-defined is a special case of predicate-defined.
  • Delete from superclass ⇒ deleted from all subclasses.

7.11 Union Types Using Categories
CATEGORY (UNION TYPE) 🔴 CRITICAL

Definition: Represents a single superclass/subclass relationship with more than one superclass. The subclass (category) represents a collection of objects that is a subset of the UNION of distinct entity types.

Example: OWNER ⊆ PERSON ∪ BANK ∪ COMPANY (owner of a vehicle).

Properties: attribute inheritance works more selectively (each member inherits only from the superclass it actually belongs to); a category can be total or partial; some modeling methodologies do not have union types.

Notation: a circle with U connecting the superclasses to the category.

Example data
OWNER(OwnerID, OwnerType, SourceID): O01 BANK Bank A · O02 PERSON P01 · O03 PERSON P03 · O04 COMPANY Company X. Bank B, person P02 and Company Y are not owners → partial category.

RULE — Total category ≈ total specialization

A total category can be represented as a total (disjoint) specialization/generalization — lecture: “Total category == total disjoint specialization” (compare VEHICLE –d– {CAR, TRUCK} with REGISTERED_VEHICLE –U– {CAR, TRUCK}).

Category (union) vs Shared subclass (lattice)
Category → member of one of the superclasses (UNION); selective inheritance.
Shared subclass in a lattice → member of all its superclasses (INTERSECTION); inherits from all.
The difference: union = “OR” (one parent's attributes); lattice = “AND” (all parents' attributes).
Category vs Generalization (superclass)
Generalization → one superclass (VEHICLE) with subclasses CAR, TRUCK: every car is a vehicle.
Category → one subclass (OWNER) with several superclasses: an owner is a person or a bank or a company.
The difference: generalization has one superclass and many subclasses; a category has many superclasses and one subclass.
🧠 What to Remember
  • Category = subset of the UNION of several superclasses; circle with U.
  • Total category = double line; partial = single.
  • Union (selective inheritance) vs lattice (intersection).

7.12 Design Choices for Specialization/Generalization

Many specializations and subclasses can be defined to make the conceptual model accurate — which to choose?

RULE — Design guidelines
  • If all subclasses have few specific attributes and no specific relationships, they can be merged into the superclass, or replaced by one or more type attributes that specify the subclass(es) each entity belongs to.
  • Union types and categories should generally be avoided — prefer total specialization/generalization.
  • Choice of disjoint/overlapping and total/partial is driven by the rules of the mini-world. Default: overlapping and partial.
Example 1 — Keep subclasses
EMPLOYEE –d– ENGINEER (Specialization; designs projects), MANAGER (Bonus; manages departments): subclasses have unique attributes and different relationships → keep the specialization.
Example 2 — Merge
STUDENT –d– UNDERGRADUATE, POSTGRADUATE with no unique attributes/relationships → merge into STUDENT(StudentID, Name, Type).
Example 3 — Overlapping
STUDENT –o– INTERNATIONAL, SCHOLARSHIP → STUDENT(StudentID, Name, International, Scholarship) or a Type with values International, Scholarship, Both (or two Yes/No attributes).

🧠 What to Remember
  • Few attributes + no relationships → merge / type attribute.
  • Avoid categories; default = overlapping, partial.

7.13 Data Abstraction Concepts

Four abstraction concepts: classification & instantiation, identification, specialization & generalization, aggregation & association.

ClassificationInstantiation
Systematically assigning similar objects/entities to object classes / entity types; objects sharing the same types of attributes, relationships and constraints are grouped into classesInverse of classification: generation and examination of distinct objects of a class; instance related to its class by IS_A_MEMBER_OF
Defines the group: Objects → Class (CAR with Model, Color, Year)Creates/identifies members: Class (CAR) → Car 1 (Toyota, White, 2024), Car 2 (Honda, Black, 2023)
IDENTIFICATION

The abstraction process whereby classes and objects are made uniquely identifiable by means of some identifier. Needed at two levels:

  1. To distinguish among database objects and classes — entity/class names must be unique within an ER/EER diagram; attribute names must be unique within an entity type (distinct names across the DB recommended, e.g. EmpName, DeptName).
  2. To identify database objects and relate them to their real-world counterparts — e.g. EmpID = 101 identifies a specific employee in the DB and in real life.

Aggregation and association 🟡

AGGREGATION

An abstraction concept for building composite objects from their component objects (e.g. an entity and its attributes). Three types:

  1. Basic aggregation — objects (attributes) form the whole object: COMPANY is an aggregation of Cname and Caddress; JOB_APPLICANT of Ssn, Name, Address, Phone. e.g. {Cname: "ABC", Caddress: "Muscat"}.
  2. Aggregation represented as an ordinary relationship.
  3. Combining related objects into a higher-level aggregate object (composite object).
Figure 7.28 — INTERVIEW and JOB_OFFER (some interviews result in job offers, others do not)
(a) Relationship INTERVIEW between COMPANY and JOB_APPLICANT.
(b) Including JOB_OFFER in a ternary INTERVIEW — incorrect: it would mean every interview must result in a job offer.
(c) RESULTS_IN relationship participating in another relationship — not allowed in ER (no relationship among relationships).
(d) Type 3: aggregate INTERVIEW + COMPANY + JOB_APPLICANT as a composite (molecular) object related to JOB_OFFER — generally not allowed in ER but allowed by some modeling tools.
(e) Correct ER representation (Type 2): create a weak entity type INTERVIEW (identifying relationship CJI with COMPANY and JOB_APPLICANT) and relate it to JOB_OFFER by RESULTS_IN.
ASSOCIATION

Associates objects from several independent classes (relates entities by an ordinary relationship).

🧠 What to Remember
  • Classification (objects → class) vs instantiation (class → objects, IS_A_MEMBER_OF).
  • Identification at 2 levels: names unique; objects linked to real-world counterparts.
  • ER does not allow relationships among relationships → use a weak entity (INTERVIEW).

🔥 FINAL EXAM REVIEW

10–15 minute scan of the highest-priority facts.

Highest-priority facts

Critical definitions

  • Database: related recorded data with implicit meaning; mini-world (UoD); logically coherent; specific purpose.
  • DBMS: software to define, construct, manipulate, maintain, share.
  • Meta-data: DB definition in the catalog. Data model: concepts for structure, relationships, constraints.
  • Schema: description (rarely changes). State/snapshot: data at a moment. Valid state: satisfies all constraints.
  • Data independence: change schema at one level without changing the next higher level (only mapping changes).
  • Domain: set of atomic values. Degree: # attributes. r(R) ⊆ dom(A1)×…×dom(An).
  • Key: minimal superkey. PK: chosen candidate key, underlined. FK: refers to a PK.
  • Entity: thing with independent existence. Weak entity: no own key; owner; identifying relationship; total participation.
  • Category: subclass that is a subset of the UNION of several superclasses.

Critical rules & constraints

  • Entity integrity: PK ≠ NULL. Referential: FK matches existing PK (arc FK → PK).
  • Insert can violate domain, key, entity, referential (default: reject). Delete only referential → restrict / cascade / set null (not on PK part) / set default. Update of non-key: fine.
  • Constraint types: inherent (implicit) · schema-based (explicit, DDL: domain, key, NOT NULL) · application-based (semantic; triggers/assertions).
  • Flat relational model: values atomic — no composite, no multivalued; no tuple order.
  • NULL = unknown / exists but missing / not applicable.
  • Relationship attribute: 1:1 either side; 1:N → N side; M:N stays on relationship.
  • EER: delete from superclass ⇒ deleted from all subclasses; total ⇒ insert into ≥1 subclass; predicate-defined ⇒ insert into every satisfied subclass.
  • Design choice defaults: overlapping + partial; avoid union types.

Notation & numbers

  • Double rectangle = weak entity; double diamond = identifying relationship; double oval = multivalued; dashed oval = derived; underline = key.
  • Double line = total (relationship participation, specialization, category). Single = partial.
  • Circle d = disjoint, o = overlapping, U = union/category; ⊂ on line toward subclass.
  • (min,max): 0 ≤ min ≤ max, max ≥ 1; min > 0 ⇒ total.
  • COMPANY: WORKS_FOR EMP(1,1) DEPT(4,N) · MANAGES EMP(0,1) DEPT(1,1) · CONTROLS DEPT(0,N) PROJ(1,1) · WORKS_ON (1,N)/(1,N) · SUPERVISION (0,N)/(0,1) · DEPENDENTS_OF EMP(0,N) DEP(1,1).
  • Ternary: number = max when the other two are fixed; N:N:1, 1:M:N, M:N:P; all M/N ⇒ key = all participants.
  • Domain examples: GPA 0–4; employee ages 15–80; phone (ddd)ddd-dddd. ER value set: age [16,70].
