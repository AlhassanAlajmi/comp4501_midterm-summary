V & V: Verification and Validation ⭐ Must know

Verification

"Building the Product Right" (PR).

Done by Static testing. No need to run the code.

Techniques: Review, Walkthrough, Inspection (plus Informal & Technical review and Static Analysis, see Lecture 7).

Validation

"Building the Right Product" (RP).

Done by Dynamic testing. Need to run the code.

Techniques: White Box, Black Box, Grey Box (see Lecture 8, Lecture 9).

⚠️ Common confusion

PR = Product Right = Verification = Static. RP = Right Product = Validation = Dynamic. Memory hook: you verify the documents and code without running them, and you validate by running the software against what the user needs.

Lecture 2

Testing Principles & Error – Bug – Defect – Fault – Failure

The most "conceptual" lecture: what testing can and cannot prove, the 7 principles, and the error → fault → failure chain with test-case tables. ⭐ Very likely exam material.

Testing is a semi-decidable problem ⭐ Must know

⭐ Must know – Dijkstra, 1972

"Software testing can be used to show the presence of defects, but never to prove their absence."

  • If the software fails on at least one test case → we are sure there is a bug (fault, defect) / error in the software.
  • If the software behaves well on a finite set of test cases → we cannot conclude that the software is error free.
  • Nevertheless, testing gives confidence in the quality of the software.
  • Use systematic testing techniques, not random test cases, to test both the functional and the non-functional requirements.

The 7 Principles of Testing ⭐ Must know

#PrincipleWhat it means (professor's wording, condensed)
P1Testing shows presence of defects, not their absenceDijkstra 1972. One failing test case proves an error exists. Passing tests prove nothing about absence.
P2Exhaustive testing is not possibleIt is usually impossible to test all inputs, combinations and execution paths, so use systematic techniques, not random test cases. Good behaviour on a finite set ≠ defect-free, but it gives confidence.
P3Defect ClusteringA small number of modules contain most of the defects. This is the Pareto law applied to testing: ≈ 80% of defects are found in 20% of modules.
P4Pesticide ParadoxRepeating the same set of tests stops finding new defects. Fix: regularly review and revise test cases and add new, different ones.
P5Testing is Context DependentDifferent software needs different approaches, methodologies, techniques and types of testing. E.g., testing an e-commerce site ≠ a commercial off-the-shelf app, and a retail POS system ≠ an ATM machine.
P6Absence of Errors Fallacy (Illusion)Software that is 99% bug-free can still be unusable if it was tested thoroughly against the wrong requirement. Testing must also check that the software addresses the business needs. This problem leads to the next principle.
P7Early Testing (saves time & money)Start testing as early as possible in the SDLC so that defects in the requirements or design phase are caught early. It is much cheaper to fix a defect early, so start finding bugs the moment the requirements are defined.
⚠️ Common confusion
  • P1 vs P6: P1 says passing tests can't prove there are no defects. P6 says that even no defects doesn't mean the system is useful (it may meet the wrong requirements).
  • P2 vs P4: P2 says you can't test everything, so choose tests systematically. P4 says the same tests lose power over time, so keep revising them.

Error → Fault → Failure (and Bug / Defect) ⭐ Must know

TermDefinition (Lecture 2)Example from the notes
ErrorDeveloper coding error, typing error, missing error, or misunderstanding the requirementsTyping x * x; instead of 2 * x; · typing x + 3 instead of x + 8
FaultCaused by the error. An internal state of the program that causes the software to fail: an invalid step / inappropriate data definitionThe wrong expression in the code, e.g., n * n * n instead of n * 3
Defect / Bug"Bug" is the informal name of Defect and also of Fault—
FailureCaused by the fault. The result is different from what the user expects, i.e., the externalization of the faultA button is not clickable / disabled when it should be · the expected value is true and the program gives false
⭐ Must know

A fault may not imply a failure if the test cases do not have enough coverage. A fault can exist in the code (and even be executed) while the output still matches the expectation. It becomes a failure only when the wrong internal state shows up in the external result.

⚠️ Common confusion
  • Error is the human action. Fault is what that action leaves in the program (internal). Failure is what the user observes (external).
  • "Fault exists" ≠ "failure occurs". To classify a test case, compare the actual internal state with the expected internal state (fault visible?), then the actual output with the expected output (failure?).
  • The definition of Defect in Lecture 5 ("a fault or a bug in the software") agrees with this: defect = fault = bug.
🎯 Exam tip: method for "fault / failure" questions
  1. Find the error (the wrong line) and write the correct version.
  2. For the given input, compute the state with the buggy code ("Actual state in RAM") and with the correct code ("Expected state").
  3. Compare the conditions (T/F) and the intermediate values. Do they differ? Then the fault shows up internally.
  4. Compare the outputs. Same → fault without failure. Different → fault with failure.
  5. If the faulty statement is never reached, the run is without fault and without failure.

Generic process

Process

A structured set of coordinated activities required to develop a SW system.

Any process is characterized by:

  1. A set of coordinated activities
  2. Artifacts (deliverables) of each activity
  3. People who perform the activities (skilled roles & responsibilities)
  4. The modeling techniques and tools that assist people
  5. Milestones

All software processes involve: Specification (what the system should do) · Design (organization of the system) · Implementation (coding) · Testing (checking it does what the customer wants) · Evolution / Maintenance (changing it as customer needs change).

Fig. 3.2 (detailed): Start → A1 → Review/Retrospective at a milestone → A2 → … → Ai → … → An → End. Each activity uses MT&T (modeling techniques & tools) and produces an artifact, and an artifact can feed the next activity. A review can send the work back to an earlier activity.

Levels of Testing

5 levels that depend on each other (V-Model): Unit → Integration → System → Acceptance, plus Regression. They are illustrated on the SIS GPA system (class diagram, multi-tier architecture, realization).

1. Unit Testing ⭐ Must know

Unit testing

Testing the individual unit of a system, where a unit is the smallest testable part of the software. A unit may be:

  • a class, e.g., User / Student / Course / Grade
  • a method within a class, e.g., ComputeTotal(), getCH(), convert()
  • a component: a piece of code with a required interface and a provided interface (UML)
  • a function (e.g., in the functional paradigm, or a function in Python)
A unit should be tested by Static Testing

Informal review · Review · Walkthrough · Inspection · Code analysis

…and by Dynamic Testing

Functional testing (Black Box) · Structural testing (White Box)

Tools: most programming languages have their own: JUnit (Java), PyUnit (Python), JaCoCo, CheckStyle.

2. Integration Testing ⭐ Must know

Integration testing

The second level. It comes after unit testing, sometimes in parallel. It mainly tests:

  • the data flow between two units, e.g., Course ↔ Grade, Grade ↔ Convertor
  • the API of the units: the unit's interface, e.g., convert(String) → float, or a standard REST API of a resource (get, post, put, delete…)

Primary purpose: identify the defects at the interaction between integrated units, i.e., evaluate the accuracy of communication among the modules.

5. Regression Testing ⭐ Must know

Regression testing

Performed to verify that a fixed bug hasn't resulted in another functionality or business-rule violation. The intent is to ensure that a change, such as a bug fix, does not uncover another fault in the application. (May be seen as part of system testing.)

  • Tests the new changes to verify they did not affect any other area of the application.
  • Mitigates risks.
  • Increases test coverage without compromising timelines.

A verification method / process / technique used to check defects in software without executing the code. It may be done manually or with tools. Two types of techniques:

The compiler as a static tool

Violations of the programming language syntax are detected and reported as a fault or warning. Many compilers also:

  • check correct data type usage (strict typing)
  • detect undeclared variables
  • detect unreachable code
  • detect overflow/underflow of field boundaries (static addressing)
  • check interface consistency
  • detect the use of all labels as jump start or jump target

Data Flow Analysis & anomalies ⭐ Must know

Checks the usage of data on paths through the code. It cannot always detect defects, so we speak of anomalies: an inconsistency that can lead to failure but doesn't necessarily. An anomaly may be flagged as a risk (e.g., reading a variable without initialization, or never using a variable's value).

3 states of a variable
d – Defined
the variable is assigned a value
r – Referenced
its value is read and/or used
u – Undefined / k – killed
it has no defined value
3 data flow anomalies
ur
an undefined value is read: use before initialization
du
assigned a value that becomes undefined without being used
dd
assigned a second value while the first was not used
📝 Example: swap two integers if they are not equal
void swap (int x, int y) {
  int temp;
  if (x != y) {
     x = temp;      // temp read before it is initialized  → ur (temp)
     x = y;         // x assigned again, first value unused → dd (x)
     temp = y;      // temp assigned, then function ends   → du (temp)
  }
}
  • ur-anomaly of temp: temp is local to the function. Its first use is on the right side of an assignment while it is still undefined (not initialized at declaration). Compilers detect this at a high warning level.
  • du-anomaly of temp: in the last assignment temp gets a value that can't be used anywhere, because temp is only valid inside the function.
  • dd-anomaly of x: x is on the left side of two consecutive assignments. Either the first assignment can be dropped, or a use of the first value was forgotten.
🧠 Remember

Not all anomalies are obvious, so tools are needed for efficiency. Not every anomaly leads to incorrect behavior: a du-anomaly may have no direct effect and the program could still run.

🎯 Exam tip

Read the two letters as "first state → next state" on a path: u→r (read garbage), d→u (wasted value), d→d (overwritten value).

Control Flow Analysis: the Control Flow Graph (CFG) ⭐ Must know

  • The program structure is represented by a CFG: a statement → node, a sequence of statements → also one node, selection (if) and iteration → decision, flow → arrow.
  • Each branch is shown as a separate path, and loops are arrows looping back to the loop condition node.
  • The CFG detects anomalies such as jumps out of a loop body or several exits of the program. These may not lead to failure, but they violate the principles of structured programming.
  • Graph theory then suggests a basis set of test cases, and the CFG is the basis for computing cyclomatic complexity.

Cyclomatic Complexity V(G) (McCabe, 1976) ⭐ Must know

V(G) = e − n + 2p    e = number of edges · n = number of nodes · p = number of connected programs (generally 1)
V(G) = number of predicates (conditions) + 1   =   number of closed regions + 1
  • Measures the structural complexity of the code.
  • V(G) = the number of independent paths.
  • V(G) determines the number of test cases needed to reach a given % of coverage.

Dynamic testing = validation that checks defects by executing the code. There are three types: Black Box (functional), White Box (structural) and Grey Box (a mixture).

1. Equivalence Partition / Class ⭐ Must know

Equivalence class

The domain of possible input data is partitioned into equivalence classes. An equivalence class is a group of data where the tester considers that any test case based on any data of the class behaves the same, so testing one representative value of the class is sufficient.

  • Positive test cases: all representative values (plus the boundaries).
  • Negative test cases: every invalid equivalence class leads to a negative test case.
  • Provide one positive test case for each class.
Equivalence Class Coverage = number of tested equivalence classes / total number of equivalence classes

2. Boundary Value Analysis (BVA) ⭐ Must know

Boundary

Applies when the data domain has boundaries [b1, b2]. Values with b1 ≤ v ≤ b2 are positive. Values with v < b1 or v > b2 are negative. Errors typically sit in the condition of the if statement, e.g., if (v < b2) instead of if (v <= b2).

BVA Coverage = number of tested boundary values / total number of boundary values

Lecture 9

Dynamic Testing: White Box (Coverage)

Structural testing based on the structure of the code, almost always on its CFG. ⭐ Expect "how many test cases / what coverage" questions on the examples below.

Definition & application ⭐ Must know

White box testing
  • A type of dynamic testing that aims at validating the software by testing the behavior of the units.
  • It is structural testing, since it tests the structure of the code. Also known as Glass, Clear or Transparent box.
  • The source code must be available, and sometimes it must be possible to manipulate it (add code).
  • Generic idea: execute every part of the code of the unit at least once. Flow-oriented test cases are identified by analyzing the program logic, then executed.
  • Applies to the Unit and Integration levels.
⭐ Must know

The expected results must be determined from the requirements or specifications, not from the code, in order to decide whether an execution resulted in a failure.

Techniques (aka Coverage): theoretical vs practical ⭐ Must know

Theoretical (costly, many test cases)

Path · Multiple Condition · Mutation

Practical (most used, less expensive)

Statement · Branch/Decision · Condition · MC/DC · Data Flow

🧠 Remember the subsumption rules (as stated in the notes)
  • Branch/Decision subsumes Statement (100% branch ⇒ 100% statement, not the reverse).
  • Condition does NOT subsume Branch/Decision.
  • Branch + Condition subsumes Branch and Condition.
  • MC (Multiple Condition) subsumes MC/DC, and MC/DC leads down to Branch & Condition in the figure.
  • Path subsumes only Branch. Path does NOT subsume MC or MC/DC.
  • Branch coverage ≤ V(G) ≤ Number of paths, and the number of paths is indefinite in a CFG with a loop.

The CFG and V(G) used here are the same as in Lecture 7. The complexity can be computed as e − n + 2p, closed regions + 1 (with nested predicates), or number of conditions + 1.

4. Multiple Condition Coverage (MC)

Tests all combinations of the atomic conditions' T/F values. It is very expensive: 2ⁿ test cases for n conditions (theoretical technique). For 3 conditions that is 2³ = 8 test cases, the "8 theoretical test cases" of the MC/DC example. The notes also warn that with x = 0 "we are in trouble" if not all conditions are covered.

5. Modified Condition / Decision Coverage (MC/DC) ⭐ Must know

Covers only the conditions that affect the outcome, not all combinations. Keep a pair of test cases for a condition when:

  1. the value of that condition changes (T → F),
  2. the values of the other conditions stay unchanged,
  3. the outcome is different.

6. Path Testing & Coverage

  • Paths = the executable statements from the entry node to the exit node. Path testing covers the independent paths. It is a robust strategy that ensures all program routes are traversed at least once.
  • For Fig. 3, branch coverage used the loop twice: TC1 a-b-f-g-h-d-e (no repetition) and TC2 a-b-f-g-i-g-h-d-e (repetition). But a loop usually repeats many times: a-b-f-g-i-g-i-g-h-d-e, a-b-f-g-i-g-i-g-i-g-h-d-e, …
  • ⇒ An indefinite number of paths in a CFG with a loop (computable only if the number of iterations is known), so an indefinite number of test cases. Still, translate the code into a CFG and derive some test cases.
  • Path coverage analyzes all the program's pathways and is more effective than branch coverage, which is handy for sophisticated applications.
⭐ Must know

Path coverage subsumes only Branch coverage. It does NOT subsume MC or MC/DC.

8. Mutation Coverage ⭐ Must know

  • A mutant of a piece of code is the same code with a small change in the statement(s), the data or the condition(s), such as negating a condition.
  • Introduce small "mutations" into the code, then run the existing test suite against the mutant to see if the tests detect the change. E.g., an invalid mutant: use if (x >= 0) instead of if (x < 0).
  • Killed mutant: detected by the test suite (the output differed between the original and the mutant). The tests are able to detect the change.
  • Survived (alive) mutant: not caught by the test suite. Not desirable, since the goal is to kill as many mutants as possible.
Mutation Score = mutants killed / total mutants (killed + survived)
Type of mutationChange
Value (Data) mutationChange the value of a parameter, a variable or a constant
Statement mutationChange or remove a statement
Condition (Decision) mutationChange the operator in a condition
⚠️ Common confusion

Mutation testing measures the quality of the test suite, not of the code. A high score means the tests are good at catching changes. A survived mutant points to a missing or weak test.

F. Common exam traps

  • Saying "the program passed all tests, so it has no bugs". That is wrong (P1, Dijkstra).
  • Calling a fault a failure. A fault can run without failure (Award TC1/TC2, temperature TC1).
  • Mixing up PR and RP: PR = Verification = Static, RP = Validation = Dynamic.
  • Thinking 100% statement coverage means 100% branch coverage. Empty else edges are missed.
  • Thinking condition coverage implies branch coverage. It doesn't (x = 0 / division-by-zero example).
  • Thinking path coverage subsumes MC/DC. It subsumes only branch.
  • Swapping stub and driver. Stub = callee (TDA), driver = caller (BUA).
  • Walkthrough: author leads. Technical review: author absent. Inspection: moderator, checklist, scribe.
  • EP uses one representative per class. BVA tests the edges (e.g., 0, 1, 2 and 7, 8, 9 → 6 TCs).
  • Decision-table test cases are ≤ rules, and impossible rules are not executable (triangle: 11 rules → 8 TCs).
  • Chow's 0-switch = single transitions, 1-switch = double.
  • In white box, the expected output comes from the specification, not the code.
  • Acceptance defects count as product failure, system-test defects get fixed.
  • Regression is best automated. Exploratory / usability testing is best manual.

G. Problem-solving reminders

Fault / failure tables
  1. Locate the error and write the correct line.
  2. Trace the actual (buggy) and expected (correct) state for each variable and condition.
  3. Internal difference → fault visible. Output difference → failure.
  4. Faulty line not reached → no fault, no failure.
  5. For || vs &&: make exactly one atomic condition true.
CFG & V(G)
  1. Number the statements and merge pure sequences if asked.
  2. Draw decisions with T/F edges, loops back to the condition.
  3. Count e and n, then V = e − n + 2.
  4. Check with predicates + 1 and regions + 1.
  5. List V(G) independent paths with test data.
Black-box design
  1. EP: list valid + invalid classes, one value each, coverage = tested / total.
  2. BVA: b−1, b, b+1 around each edge.
  3. DT: conditions → 2ⁿ rules → collapse don't-cares → drop impossible rules.
  4. State: list transitions, build sequences from the start state, apply Chow.
White-box coverage counts
  1. Statement: use the shortcut table.
  2. Branch: every T and F edge.
  3. Condition: each atomic T and F. Check whether branches are still missed.
  4. MC/DC: pairs where flipping one condition flips the outcome.
  5. Report coverage as covered / total = %.
