Chapter 2 — Operating System Structures

▶OS Services

What is it?

The OS provides an environment to run programs, and services to programs and users. The slides split them into two sets.

Set 1 — Helpful to the userWhat it means
User interface (UI)CLI, GUI, touch-screen, or batch
Program executionLoad program into memory → run it → end it normally or abnormally (indicating error)
I/O operationsA running program may need I/O (a file or an I/O device)
File-system manipulationRead/write, create/delete, search, list file info, permission management
CommunicationsProcesses exchange info on the same computer or over a network — via shared memory or message passing (packets moved by the OS)
Error detectionErrors in CPU/memory hardware, I/O devices, user programs → OS takes the right action for each. Debugging facilities help users/programmers.
Set 2 — Efficient operation of the system itself (resource sharing)What it means
Resource allocationGive CPU cycles, main memory, file storage, I/O devices to multiple users/jobs
LoggingKeep track of which users use how much and what kinds of resources
Protection & securityProtection = all access to resources is controlled (processes don't interfere). Security = defend from outsiders: user authentication, defending external I/O devices from invalid access.
✅ Remember

Only 3 services are in the "system" set: resource allocation, logging, protection & security. Everything else helps the user.

❌ Common mistake

Putting error detection or communications in the system-efficiency set. They are user-helpful.

🔀 Common confusion — Protection vs Security

Protection = inside control (who may access what). Security = keeping outsiders out (passwords/authentication).

💡 Example

A server records CPU-seconds used per department for billing → logging. A password before remote login → security.

▶System Calls & APIs

What is it?

A system call is the programming interface to the services provided by the OS. Typically written in a high-level language (C or C++).

Key points

  • Programs usually use an API (Application Programming Interface) instead of calling system calls directly.
  • The 3 most common APIs: Win32 API (Windows), POSIX API (virtually all UNIX, Linux, Mac OS X), Java API (JVM).
User program
→ calls
API function
(run-time support library)
→
System-call interface
table indexed by number
→
Kernel routine
The status and any return values travel back the same way.

How a system call is implemented

  1. Each system call has a number.
  2. The system-call interface keeps a table indexed by these numbers.
  3. It invokes the right kernel routine and returns the status and any return values.
  • The caller needs to know nothing about how the call is implemented — just obey the API and know what the OS will do.
  • Most details are hidden by the API and managed by the run-time support library (functions built into libraries included with the compiler).
🔀 Common confusion — API vs System call

API = library functions the programmer calls (portable). System call = the actual request into the kernel. One API function may make one or more system calls.

💡 Example

A program written only with POSIX functions can be compiled on Linux, macOS and UNIX — not natively on Windows (Win32).

▶System-Call Parameter Passing

Often a system call needs more information than just its number (e.g., file name, buffer, size). There are 3 ways to pass parameters:

MethodHowLimit?

2. Block / tableStore parameters in a block in memory; pass the address of the block in a register. Used by Linux and Solaris.No limit

✅ Remember

Block and stack methods do not limit the number or length of parameters. Linux & Solaris use the block method.

💡 Example

A call needs 9 parameters but only 4 registers exist → store the 9 in a block and pass its address in 1 register.

  • Relocatable object file — compiled code designed to be loaded into any physical memory location.
  • Linker — combines object files into one binary executable, and brings in libraries.
  • Loader — brings the executable from disk into memory so it can run.
  • Relocation — assigns final addresses to program parts and adjusts code and data to match.
  • Modern general-purpose systems don't link libraries into executables; they use dynamically linked libraries (DLLs in Windows): loaded as needed, shared by all programs using the same version (loaded once).

🔀 Static vs Dynamic linking

Static: library code copied into every executable (bigger files, duplicate copies in memory). Dynamic: library loaded once at run time when needed and shared.

▶Why Applications are OS-Specific (ABI)

An app compiled on one OS usually won't run on another OS — because each OS has its own unique system calls and its own file formats.

3 ways to make an app run on multiple OSes

  1. Write it in an interpreted language (Python, Ruby) whose interpreter exists on many OSes.
  2. Use a language with a VM that contains the running app (Java).
  3. Use a standard language (C) and compile separately on each OS.
✅ Remember

ABI (Application Binary Interface) = the architecture equivalent of an API: defines how binary code components interface for a given OS on a given architecture/CPU.

❌ Common mistake

Thinking the same OS ⇒ same ABI. A different CPU architecture (ARM vs Intel) means a different ABI.

▶OS Structures: Monolithic, Layered, Microkernel, Modules, Hybrid

A general-purpose OS is a very large program, so it needs a structure. Examples: simple (MS-DOS), more complex (UNIX), layered (an abstraction), microkernel (Mach).

1. Monolithic — original UNIX

  • Limited by hardware → limited structuring. Two parts: system programs + kernel.
  • Kernel = everything below the system-call interface and above the hardware: file system, CPU scheduling, memory management… → many functions in one level.
  • Traditional UNIX: "beyond simple but not fully layered". Linux = monolithic plus modular.

2. Layered approach

Layer N — user interface
…
Layer 1
Layer 0 — hardware
Each layer uses functions and services of only lower-level layers.

3. Microkernel (e.g., Mach; Mac OS X's Darwin is partly based on Mach)

  • Moves as much as possible from the kernel into user space.
  • User modules communicate using message passing.
Benefits ✅Detriment ❌
• Easier to extend
• Easier to port to new architectures
• More reliable (less code in kernel mode)
• More secure		Performance overhead of user-space ↔ kernel-space communication

4. Loadable kernel modules (LKMs)

  • Used by many modern OSes (Linux, Solaris). Object-oriented approach.
  • Each core component is separate, talks to others over known interfaces, is loadable as needed within the kernel.
  • Similar to layers but more flexible.

5. Hybrid systems

Most modern OSes are not one pure model; they combine approaches for performance, security, usability.

OSHybrid description
Linux, SolarisKernel in kernel address space (monolithic) + modular (dynamic loading)
WindowsMostly monolithic + microkernel for different subsystem personalities
Mac OS XHybrid, layered: Aqua UI + Cocoa; kernel = Mach microkernel + BSD Unix parts + I/O kit + dynamically loadable modules (kernel extensions)

💡 Example

Need monolithic speed but want to add a driver without rebooting → monolithic + LKMs (Linux style). File system moved to user space and became slower → microkernel message-passing overhead.

🔀 Layers vs Modules

Layers: a layer may only call layers below it. Modules: any module can talk to any other through known interfaces, and modules load when needed.

System boot

  1. Power on → execution starts at a fixed memory location.
  2. A small bootstrap loader (BIOS) in ROM/EEPROM locates the kernel, loads it into memory, starts it.

Chapter 3 — Processes

▶Process Concept & Memory Layout

What is it?

A process is a program in execution. It progresses in sequential fashion — no parallel execution of instructions of a single (single-threaded) process.

Stack ↓
params, return addresses, locals

Heap ↑

Parts of a process

  • Text section — program code
  • Current activity — program counter + processor registers
  • Stack — temporary data: function parameters, return addresses, local variables
  • Data section — global variables
  • Heap — memory allocated dynamically at run time
🔀 Program vs Process

Program = passive (executable file on disk). Process = active. A program becomes a process when it's loaded into memory (started by GUI click, command line…). One program can be several processes (e.g., 3 users running the same editor = 1 program, 3 processes).

💡 Example
int count;            // Data (global)
int main(int x){       // x → Stack (parameter)
  int i;               // Stack (local)
  int *p = malloc(40); // the 40 bytes → Heap
}                      // the code itself → Text

▶Process Scheduling Queues & Context Switch

The process scheduler picks which available process runs next on a CPU core. Goal: maximize CPU use, quickly switch processes onto the core.

  • Ready queue — processes in main memory, ready and waiting to execute.
  • Wait queues — processes waiting for an event (e.g., I/O).
  • Processes migrate among the queues.
Ready queue
→
CPU
→
I/O request → I/O wait queue → back to ready
time slice expired → back to ready
fork child / wait for interrupt → wait → back to ready

Context switch

  1. CPU switches to another process.
  2. Save the state (context) of the old process into its PCB.
  3. Load the saved state of the new process from its PCB.
  • Context-switch time is pure overhead — no useful work is done.
  • More complex OS and PCB → longer switch.
  • Depends on hardware support: some CPUs have multiple register sets → multiple contexts loaded at once → faster.
✅ Remember

Context = what's stored in the PCB. Switching = save old PCB + load new PCB = pure overhead.

▶Process Termination: zombie, orphan, cascading
  • Process runs its last statement → calls exit() → OS deletes it. Status goes back to the parent via wait(); resources are deallocated.
  • pid = wait(&status); returns the status and pid of the terminated child.
  • Parent may kill a child with abort() because: child exceeded allocated resources; task no longer required; parent is exiting and the OS doesn't allow a child to continue without its parent.
  • Cascading termination — when a process terminates, all its children, grandchildren… are terminated, initiated by the OS (on OSes that don't allow orphans).
ZombieOrphan
Who has ended?The childThe parent

✅ Remember

Zombie = dead child, living parent who isn't waiting. Orphan = living child, dead parent.

▶Producer–Consumer, Bounded Buffer & Race Condition

Producer makes information that a consumer uses.

VariationProducerConsumer
Unbounded bufferNever waitsWaits if buffer empty
Bounded buffer (fixed size)Waits if all buffers fullWaits if buffer empty

Shared-memory bounded buffer (in / out solution)

#define BUFFER_SIZE 10
item buffer[BUFFER_SIZE]; int in = 0, out = 0;
/* Producer */ while (((in + 1) % BUFFER_SIZE) == out) ;  /* full → wait */
               buffer[in] = next_produced; in = (in + 1) % BUFFER_SIZE;
/* Consumer */ while (in == out) ;                         /* empty → wait */
               next_consumed = buffer[out]; out = (out + 1) % BUFFER_SIZE;
ConditionFormula
Emptyin == out
Full(in + 1) % N == out
Items in buffer(in − out + N) % N
Max itemsN − 1 (one slot always empty)

Using all N slots → add counter

  • counter = number of full buffers, starts at 0. Producer waits while counter == BUFFER_SIZE, then counter++. Consumer waits while counter == 0, then counter--.

Race condition

counter++ is really 3 steps: reg1 = counter; reg1 = reg1 + 1; counter = reg1 (same for counter-- with reg2). If they interleave:

StepAction (counter = 5)Result
S0producer reg1 = counterreg1 = 5
S1producer reg1 = reg1 + 1reg1 = 6
S2consumer reg2 = counterreg2 = 5
S3consumer reg2 = reg2 − 1reg2 = 4
S4producer counter = reg1counter = 6
S5consumer counter = reg2counter = 4 ❌ (should be 5)
✅ Remember

Possible final values: 4, 5 or 6 — the result depends on the order of execution = race condition. The first (in/out) solution has no race because each variable has only one writer (producer writes in, consumer writes out).

▶IPC Examples: POSIX Shared Memory, Mach, Windows ALPC

▶Client–Server: Sockets & RPC

Sockets

  • A socket = endpoint for communication = IP address + port. Example: 161.25.19.8:1625 = port 1625 on host 161.25.19.8.
  • Communication happens between a pair of sockets.
  • Ports below 1024 are well known (standard services).
  • 127.0.0.1 = loopback (the same machine).
  • Java socket types: TCP (connection-oriented), UDP (connectionless), MulticastSocket (send to many recipients). Slide example: a "Date" server and client.

Remote Procedure Call (RPC)

Makes calling a procedure on another networked machine look like a local call. Uses ports to tell services apart.

→

→ message →

  • Stub = client-side proxy for the real procedure on the server. On Windows, stubs are compiled from MIDL.
  • XDR (External Data Representation; slide writes "XDL") handles different architectures: big-endian vs little-endian.
  • Remote = more failure cases → messages delivered exactly once rather than at most once.

🔀 Marshalling vs XDR vs Matchmaker

Marshalling = packing parameters into a message. XDR = neutral data format (endianness). Matchmaker = finds the server's port.

Chapter 4 — Threads & Concurrency

▶Threads: Motivation & Benefits

What is it?

A thread is a unit of execution inside a process. Most modern apps (and kernels) are multithreaded: e.g., one thread updates the display, one fetches data, one spell-checks, one answers network requests.

Single-threaded processcode · data · files
registers · 1 stack · 1 PC
Multithreaded processShared: code · data · files
Per thread: registers · stack · PC
  • Process creation is heavy-weight; thread creation is light-weight. Threads can simplify code and increase efficiency.
  • Multithreaded server: request arrives → server creates a thread to service it → resumes listening.
BenefitMeaningExample
ResponsivenessExecution continues even if part of the process is blocked — important for UIsEditor keeps accepting typing while saving

🔀 Process vs Thread

Process = a program in execution with its own address space (code, data, heap, files). Thread = a path of execution inside a process: shares code/data/files, but has its own registers, PC and stack.

▶Amdahl's Law

Tells you the maximum speedup from adding cores to an app that has both serial and parallel parts.

speedup ≤ 1 / ( S + (1 − S) / N )

S = serial portion (fraction) · N = number of cores. As N → ∞, speedup → 1 / S.

💡 Worked example (slides)

75% parallel, 25% serial (S = 0.25), N = 2:
1 / (0.25 + 0.75/2) = 1 / 0.625 = 1.6×
N = 4: 1 / (0.25 + 0.1875) ≈ 2.29× · N = ∞: 1 / 0.25 = 4× max.

✅ Remember

The serial portion has a disproportionate effect: even with infinite cores you can't beat 1/S. (The slides also ask whether the law fits contemporary multicore systems.)

❌ Common mistake

Using the parallel fraction as S. S is the serial part. Convert % to a decimal first.

▶Thread Libraries & Pthreads
  • A thread library gives the programmer an API to create and manage threads. Implemented either entirely in user space or as a kernel-level library supported by the OS.
  • Pthreads = POSIX standard (IEEE 1003.1c) API for thread creation and synchronization.
  • It is a specification, not an implementation: the API defines behaviour; library developers decide the implementation. May be user-level or kernel-level. Common in UNIX (Linux, Mac OS X).
pthread_attr_init(&attr);                      /* default attributes   */
pthread_create(&tid, &attr, runner, argv[1]);  /* create thread        */
pthread_join(tid, NULL);                       /* wait for it to end   */
pthread_exit(0);                               /* thread ends itself   */
/* joining 10 threads: for (i=0;i<10;i++) pthread_join(workers[i], NULL); */
❌ Common mistake

"Pthreads is Linux's thread implementation." No — it is a specification.

▶Implicit Threading: Thread Pools, Fork-Join, OpenMP

Implicit threading = threads are created and managed by compilers and run-time libraries, not by the programmer. Popular because correctness gets harder as thread counts grow.

Thread pools

Create a number of threads in a pool where they wait for work.

  1. Usually slightly faster to service a request with an existing thread than create a new one.
  2. Allows the number of threads to be bound to the size of the pool (prevents running out of resources).
  3. Separates the task from the mechanics of creating it → different strategies, e.g., run tasks periodically.

The Windows API supports thread pools.

Fork-Join

Multiple tasks are forked, then joined.

Task(problem):
  if problem is small enough → solve it directly
  else: subtask1 = fork(new Task(subset of problem))
        subtask2 = fork(new Task(subset of problem))
        result1 = join(subtask1); result2 = join(subtask2)
        return combined results

Java: ForkJoinTask is an abstract base class; RecursiveTask returns a result (from compute()); RecursiveAction does not.

OpenMP

  • Compiler directives + API for C, C++, FORTRAN; for shared-memory environments.
  • Identifies parallel regions. #pragma omp parallel → creates as many threads as there are cores.
  • #pragma omp parallel for → runs a for loop in parallel.
▶Threading Issues: fork()/exec() & Signals

fork() and exec() in a multithreaded process

  • Does fork() copy only the calling thread or all threads? Some UNIXes have two versions of fork.
  • exec() works as normal: replaces the entire process, including all threads.
✅ Remember

If exec() is called right after fork, copying all threads is wasted → duplicating only the calling thread is enough.

Signal handling

  • Signals (UNIX) notify a process that an event happened.
  • Steps: signal generated by an event → delivered to a process → handled.
  • Two handlers: default (every signal has one; the kernel runs it) or user-defined (overrides default).
  • Single-threaded: delivered to the process. Multithreaded — 4 options:
    1. To the thread to which the signal applies
    2. To every thread
    3. To certain threads
    4. Assign one specific thread to receive all signals
💡 Example

Thread T2 makes an illegal memory access (synchronous signal) → deliver to T2.

▶Thread-Local Storage & Scheduler Activations

Thread-Local Storage (TLS)

  • Each thread gets its own copy of data.
  • Useful when you don't control thread creation (e.g., thread pool).
  • Different from local variables: locals live only during one function call; TLS is visible across function calls.
  • Similar to static data, but unique to each thread.
🔀 Global vs Local vs TLS

Global = one copy shared by all threads. Local = one copy per function call. TLS = one copy per thread, lasting across calls.

  • Upcall = communication from the kernel to the upcall handler in the thread library. This lets the app keep the correct number of kernel threads.

Chapter 5 — CPU Scheduling

▶Basic Concepts: Burst Cycle, Scheduler, Preemption, Dispatcher
  • Max CPU utilization comes from multiprogramming.
  • CPU–I/O burst cycle: a process alternates CPU bursts and I/O bursts (waits).
  • Histogram: many short CPU bursts, few long ones. CPU-burst distribution is the main concern.
  • CPU scheduler: picks a process from the ready queue and gives it a CPU core.
🔀 CPU-bound vs I/O-bound

CPU-bound = long CPU bursts, little I/O (e.g., video encoding). I/O-bound = many short CPU bursts with lots of I/O waiting (e.g., a text editor). In FCFS, I/O-bound jobs stuck behind a CPU-bound job = convoy effect.

When does scheduling happen?

#Process…Choice?
1Running → Waiting (e.g., I/O request)No choice — must pick new

3Waiting → Ready (e.g., I/O done)Choice

Non-preemptivePreemptive

Risk—Race conditions on shared data (preempted mid-update; another process reads inconsistent data)

Dispatcher

Gives the CPU to the process the scheduler chose: (1) switch context, (2) switch to user mode, (3) jump to the right place in the user program.

Dispatch latency = time for the dispatcher to stop one process and start another.

🔀 Scheduler vs Dispatcher

Scheduler decides who runs. Dispatcher does the switch.

▶Scheduling Criteria & Formulas
CriterionMeaningGoal
CPU utilizationKeep the CPU as busy as possibleMax
Throughput# processes that complete per time unitMax

Waiting timeTime spent waiting in the ready queueMin

Turnaround (TAT) = Completion − Arrival
Waiting (WT) = Turnaround − Burst
Response (RT) = First time on CPU − Arrival
Throughput = processes completed ÷ time
🎯 How to solve any scheduling problem
  1. Write the table: process, arrival, burst (and priority if given).
  2. Draw the Gantt chart step by step. At each decision point, list who is in the ready queue.
  3. Read completion times off the chart.
  4. TAT = completion − arrival → WT = TAT − burst → RT = first start − arrival.
  5. Average = sum ÷ number of processes. Double-check: the chart ends at Σ bursts (if the CPU is never idle).
▶First-Come, First-Served (FCFS)

Run processes in arrival order. Non-preemptive.

💡 Slide example — bursts P1 = 24, P2 = 3, P3 = 3

Order P1, P2, P3:

WT: P1 = 0, P2 = 24, P3 = 27 → average = 51/3 = 17

Order P2, P3, P1:

WT: P1 = 6, P2 = 0, P3 = 3 → average = 9/3 = 3 — much better!

✅ Remember

Convoy effect — short processes stuck behind a long process (e.g., one CPU-bound and many I/O-bound processes). FCFS result depends heavily on arrival order.

▶Shortest-Job-First (SJF) & Shortest-Remaining-Time-First (SRTF)

Give the CPU to the process with the shortest next CPU burst.

  • SJF is optimal: gives the minimum average waiting time for a given set of processes.
  • Problem: we don't know the next burst length → ask the user or estimate it.
  • Preemptive version = SRTF (shortest-remaining-time-first): whenever a new process arrives, re-decide using remaining times.
💡 SJF example — all arrive at 0: P1 = 6, P2 = 8, P3 = 7, P4 = 3

WT: P1 = 3, P2 = 16, P3 = 9, P4 = 0 → (3+16+9+0)/4 = 7

💡 SRTF example — (arrival, burst): P1 (0,8), P2 (1,4), P3 (2,9), P4 (3,5)
  • t=1: P2 (4) < P1 remaining (7) → preempt P1.
  • t=5: P2 done; shortest remaining: P4 (5), then P1 (7), then P3 (9).

WT = completion − arrival − burst: P1 = 17−0−8 = 9, P2 = 5−1−4 = 0, P3 = 26−2−9 = 15, P4 = 10−3−5 = 2
Average = 26/4 = 6.5 (non-preemptive SJF on the same data gives 7.75)

❌ Common mistake

In non-preemptive SJF with arrival times, only choose among processes that have already arrived when the CPU becomes free.

▶Predicting the Next CPU Burst (Exponential Averaging)

We can only estimate the next burst — assume it's similar to previous ones — then pick the process with the shortest predicted burst.

τn+1 = α · tn + (1 − α) · τn
  • tn = actual length of the n-th burst · τn+1 = predicted next burst · 0 ≤ α ≤ 1, commonly α = ½.
  • α = 0 → τn+1 = τn: recent history doesn't count.
  • α = 1 → τn+1 = tn: only the last actual burst counts.
  • Expanded: τn+1 = αtn + (1−α)αtn−1 + … + (1−α)jαtn−j + … + (1−α)n+1τ0 → older bursts get less and less weight.
💡 Example (slide figure): α = ½, τ0 = 10
Actual burst ti6464131313
Guess τi108665911

τ1 = ½·6 + ½·10 = 8 · τ2 = ½·4 + ½·8 = 6 · τ3 = ½·6 + ½·6 = 6 · τ4 = ½·4 + ½·6 = 5 · next = ½·13 + ½·5 = 9 …

✅ Remember

SJF is a kind of priority scheduling where priority = inverse of predicted next burst.

▶Round Robin (RR)

Each process gets a small unit of CPU time = time quantum q (usually 10–100 ms). When q runs out, the process is preempted and put at the end of the ready queue. A timer interrupt fires every quantum.

  • n processes, quantum q → each gets 1/n of the CPU in chunks of at most q. No process waits more than (n − 1)·q.
  • q large → behaves like FIFO (FCFS). q small → too much context-switch overhead — q must be large compared to context-switch time (context switch < 10 µs).
  • Rule of thumb: 80% of CPU bursts should be shorter than q.
  • Typically higher average turnaround than SJF, but better response.
💡 Slide example — q = 4, P1 = 24, P2 = 3, P3 = 3 (all at 0)

WT: P1 = 30−24 = 6, P2 = 7−3 = 4, P3 = 10−3 = 7 → avg = 17/3 ≈ 5.67 (FCFS was 17)
RT: 0, 4, 7 → avg ≈ 3.67

With arrival times, a process that arrives at the same moment another is preempted — usually the new arrival joins the queue first. Track the queue after every slice.

▶Multiple-Processor Scheduling

Architectures: multicore CPUs · multithreaded cores · NUMA systems · heterogeneous multiprocessing.

  • SMP (symmetric multiprocessing): each processor is self-scheduling. Either (a) a common ready queue or (b) a private queue per processor.
  • Multicore: several cores on one chip — faster, less power.
  • Multithreaded cores: when one hardware thread has a memory stall, the core switches to another thread.
  • Chip multithreading (CMT) / Intel hyperthreading: logical CPUs = cores × hardware threads (quad-core × 2 = 8 logical processors).
  • Two levels of scheduling: (1) OS picks which software thread runs on a logical CPU; (2) each core picks which hardware thread runs.

▶Real-Time Scheduling: RM, EDF, Proportional Share, POSIX
Soft real-timeHard real-time
Critical tasks get highest priority, but no guarantee when they runTask must be serviced by its deadline

Latencies

  • Event latency = time from when an event occurs to when it is serviced.
  • Interrupt latency = arrival of interrupt → start of its service routine.
  • Dispatch latency = time to take the current process off the CPU and switch to another. Its conflict phase: (1) preempt any process running in kernel mode; (2) low-priority processes release resources needed by high-priority ones.

Periodic tasks

Scheduler must be preemptive, priority-based (this alone only guarantees soft real-time). A periodic task has processing time t, deadline d, period p: 0 ≤ t ≤ d ≤ p; rate = 1/p.

AlgorithmPriority ruleType
Rate Monotonic (RM)Priority = 1/period → shorter period = higher priorityStatic
Earliest Deadline First (EDF)Earlier deadline = higher priorityDynamic
💡 RM works: P1 (p=50, t=20), P2 (p=100, t=35)

P1 has higher priority (shorter period). P2 is preempted at 50, finishes at 75 < 100 ✓

💡 RM fails, EDF works: P1 (p=50, t=25), P2 (p=80, t=35)

RM:

P2 finishes at 85 → misses its deadline at 80 ❌

EDF:

At t=50, P2's deadline (80) is earlier than P1's new deadline (100) → P2 keeps running, finishes at 60 ✓

Proportional share

T shares are divided among all processes; an app with N shares (N < T) gets N/T of the processor time. E.g., T = 100, N = 15 → 15%.

▶OS Examples: Linux, Windows, Solaris

Linux up to 2.5 — O(1) scheduler

  • Constant-time O(1); preemptive, priority-based; two ranges: time-sharing and real-time.
  • Higher priority → larger q. Task runnable while it has time left (active); when used up (expired) it waits until all others use theirs.
  • Per-CPU runqueue with two priority arrays (active, expired); when no active tasks remain, arrays are swapped.
  • Worked well but poor response for interactive processes.

Linux 2.6.23+ — Completely Fair Scheduler (CFS)

  • Scheduling classes, each with a priority; picks highest-priority task in the highest class. Two included: default and real-time.
  • Not fixed time slices — based on a proportion of CPU time.
  • Quantum based on nice value −20 to +19 (lower = higher priority).
  • Target latency = interval in which every task should run at least once (grows if more tasks).
  • Each task has vruntime (virtual run time) with a decay factor: lower priority → higher decay rate. Normal priority → vruntime = real run time.
  • Next task = lowest vruntime.
  • Global priorities: real-time 0–99, normal 100–139 (nice −20 → 100, nice +19 → 139; so priority = 120 + nice). Lower number = higher priority.
  • Load balancing + NUMA-aware: scheduling domains = sets of cores that share (e.g., cache) and can be balanced; keep threads from migrating between domains.

Windows

  • Priority-based preemptive; highest-priority thread runs; the dispatcher is the scheduler.
  • A thread runs until it (1) blocks, (2) uses its time slice, (3) is preempted by a higher-priority thread. Real-time threads can preempt non-real-time.
  • 32 levels: variable class 1–15, real-time class 16–31, priority 0 = memory-management thread. Queue per priority; idle thread if nothing runnable.
  • Priority classes: REALTIME, HIGH, ABOVE_NORMAL, NORMAL, BELOW_NORMAL, IDLE — all variable except REALTIME. Relative priorities: TIME_CRITICAL, HIGHEST, ABOVE_NORMAL, NORMAL, BELOW_NORMAL, LOWEST, IDLE. Class + relative → numeric priority; base = NORMAL in the class.
  • Quantum expires → priority lowered, never below base. After a wait → priority boosted (depends on what it waited for). Foreground window: 3× boost.
  • Windows 7 user-mode scheduling (UMS): apps manage threads without the kernel; efficient for many threads (e.g., C++ ConcRT).

Solaris

  • Priority-based; 6 classes: Time sharing (TS, default), Interactive (IA), Real time (RT), System (SYS), Fair share (FSS), Fixed priority (FP).
  • A thread is in one class at a time; each class has its own algorithm. Time sharing = MLFQ with a loadable table (dispatch table) set by the sysadmin.
  • Class priorities → per-thread global priority; highest runs; runs until it blocks, uses its slice, or is preempted; equal priorities → RR.

💡 Deterministic example — all at 0: P1 = 10, P2 = 29, P3 = 3, P4 = 7, P5 = 12

Little's formula

n = λ × W

n = average queue length · λ = average arrival rate · W = average waiting time in the queue. Holds in steady state for any scheduling algorithm and arrival distribution.

💡 Example

7 processes arrive per second, 14 in the queue → W = 14 / 7 = 2 seconds.

⚠️ Common Confusions

▶Side-by-side differences
Profiling vs Tracing
Profiling: periodically samples the instruction pointer → statistical trends.
Tracing: records data about a specific event (e.g., each step of a system call; strace).
Core dump vs Crash dump
Core dump: an application failed → its process memory.
Crash dump: the OS failed → kernel memory.
Monolithic kernel vs Microkernel
Monolithic: all services in the kernel, one level → fast, but harder to extend and less isolated.
Microkernel: most services in user space, message passing → extensible, portable, reliable, secure, but slower.
Layers vs Modules
Layers: each layer uses only lower layers; layer 0 = hardware, N = UI. Rigid.
Modules (LKM): separate components talk via known interfaces, loaded as needed into the kernel. More flexible.
Static vs Dynamic linking
Static: library copied into every executable.
Dynamic (DLL): loaded only when needed, one shared copy.
API vs System call vs ABI
API: source-level functions programmers call (POSIX, Win32, Java). System call: the real request into the kernel.
ABI: binary-level interface for an OS on a specific CPU architecture.
Protection vs Security
Protection: controlling access to resources inside the system.
Security: defending against outsiders (authentication).
BIOS/UEFI vs GRUB
BIOS (in ROM) is the bootstrap firmware; UEFI replaces BIOS.
GRUB: bootstrap loader that lets you choose the kernel/version/options.
Program vs Process
Program: passive file on disk.
Process: active program in execution (loaded in memory). One program → many processes.
Process vs Thread
Process: own address space; heavy-weight to create.
Thread: inside a process; shares code/data/files; own registers, PC, stack; light-weight.
Ready vs Waiting
Ready: has everything except the CPU.
Waiting: needs an event (I/O) first; goes to Ready afterwards (never straight to Running).
Zombie vs Orphan
Zombie: child ended; parent alive but hasn't called wait().
Orphan: parent ended without wait(); child still exists.
Shared memory vs Message passing
Shared memory: user processes control it; must synchronize.
Message passing: send/receive through the OS, no shared variables.
Direct vs Indirect communication
Direct: name the process; exactly 1 link per pair; automatic.
Indirect: through a mailbox; many processes; several links per pair.
Blocking vs Non-blocking
Blocking (synchronous): sender waits until received / receiver waits until available.
Non-blocking (asynchronous): sender continues / receiver gets a message or null.
Ordinary pipe vs Named pipe
Ordinary (anonymous): one-way; parent–child only.
Named: two-way; no relationship needed; several processes.
Concurrency vs Parallelism
Concurrency: several tasks make progress (possible on one core by switching).
Parallelism: several tasks run at the same instant (needs multiple cores).
Data vs Task parallelism
Data: same operation, different chunks of data.
Task: different operations on different cores.
User threads vs Kernel threads
User: managed by a thread library.
Kernel: managed by the OS kernel.
Asynchronous vs Deferred cancellation
Asynchronous: kill now.
Deferred (default): stop at the next cancellation point, then cleanup.
Local variable vs TLS
Local: exists during one function call.
TLS: per-thread copy that survives across calls.
CPU-bound vs I/O-bound
CPU-bound: long CPU bursts, little I/O.
I/O-bound: short CPU bursts, lots of I/O. Behind a CPU-bound job in FCFS → convoy effect.
Preemptive vs Non-preemptive
Preemptive: OS can take the CPU away (arrival of shorter/higher-priority job, timer). Risk: race conditions.
Non-preemptive: process keeps CPU until it terminates or waits (only cases 1 & 4).
Scheduler vs Dispatcher
Scheduler: chooses the next process.
Dispatcher: performs the switch (context, user mode, jump).
Turnaround vs Waiting vs Response time
Turnaround: arrival → completion. Waiting: only time in the ready queue.
Response: arrival → first time on CPU.
SJF vs SRTF
SJF: non-preemptive; decides only when CPU becomes free.
SRTF: preemptive; re-decides whenever a new process arrives.
Starvation vs Aging
Starvation: a low-priority process never runs (the problem).
Aging: increase priority over time (the solution).
Multilevel queue vs Multilevel feedback queue
MLQ: process stays in its queue.
MLFQ: process can move up/down between queues.
PCS vs SCS
PCS: threads of one process compete (thread library → LWP).
SCS: all threads in the system compete (kernel → CPU).
Soft vs Hard affinity · Push vs Pull migration
Soft: OS tries to keep thread on CPU. Hard: process lists allowed CPUs.
Push: periodic task moves work off busy CPUs. Pull: idle CPU takes work.
Soft vs Hard real-time
Soft: highest priority but no guarantee.
Hard: must meet the deadline.
Rate Monotonic vs EDF
RM: static priority; shorter period = higher. Can miss deadlines.
EDF: dynamic priority; earlier deadline = higher.
SCHED_FIFO vs SCHED_RR
FIFO: no time-slicing among equal priorities.
RR: time-slicing among equal priorities.

📐 Formulas
  • TAT = completion − arrival
  • WT = TAT − burst
  • RT = first run − arrival
  • Throughput = done ÷ time
  • Amdahl: 1 / (S + (1−S)/N); max 1/S
  • τn+1 = αtn + (1−α)τn (α=0 history only; α=1 last burst only)
  • Little: n = λ·W
  • RR max wait: (n−1)·q
  • Proportional share: N/T
  • Buffer items: (in − out + N) % N; max N − 1
  • n forks → 2ⁿ processes
  • Logical CPUs = cores × HW threads
  • Linux priority = 120 + nice (RT 0–99)
  • Periodic: 0 ≤ t ≤ d ≤ p, rate 1/p
⚙️ Algorithms (one line each)
  • FCFS: arrival order, non-preemptive, convoy effect
  • SJF: shortest next burst; optimal avg WT; needs prediction
  • SRTF: preemptive SJF, re-check on each arrival
  • RR: quantum q, back of queue; good response
  • Priority: smallest # first; starvation → aging; ties → RR (variant)
  • MLQ / MLFQ: several queues; MLFQ moves processes
  • RM: 1/period; EDF: earliest deadline
  • CFS: lowest vruntime
